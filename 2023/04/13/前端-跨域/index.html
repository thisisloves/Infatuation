前端 跨域

2023-04-13
  • 前端
本文总阅读量次

十年生死两茫茫，不思量，自难忘。

跨域是浏览器的同源策略

同源指协议、主机、端口三个都相同。https://a.com 和 http://a.com、https://a.com:8443、https://api.a.com 都是不同源。浏览器限制脚本读取非同源的响应、访问非同源的 DOM。限制的是读取，不是「请求绝对发不出去」。

同源策略保护的是用户浏览器里的数据，不是服务器本身。用 curl 或自己的后端去请求，没有这层限制。

没有这层限制时会怎样

若 iframe 能任意读另一个源的 DOM，攻击者可以把银行页面嵌进自己的站点，用户输入的内容就能被外层页面拿走。所以非同源 iframe 不能访问内部 document。

若脚本能任意读另一个源的 AJAX 响应，恶意页面就能带着用户的 Cookie 去读银行接口的返回值。浏览器会把带 Cookie 的请求发出去（这是 CSRF 要单独防的事），但默认不把响应交给恶意页面的脚本。CSRF 与「读响应」是两件事：前者关心请求是否被执行，后者才由同源策略拦住。

CORS

CORS 是服务端用响应头声明：哪些源可以用脚本读这个响应。浏览器先看请求算不算简单请求。方法为 GET、HEAD、POST，且头在安全名单里、Content-Type 为 text/plain、application/x-www-form-urlencoded、multipart/form-data 之一，才是简单请求。带 Authorization、Content-Type: application/json 或 PUT、DELETE，会先发 OPTIONS 预检。

要点：

  • 需要带 Cookie 时，前端 fetch 写 credentials: "include"，XHR 写 withCredentials = true。
  • 此时 Allow-Origin 必须是具体源，不能是 *，还要 Allow-Credentials: true。
  • 不要把请求里的 Origin 无条件反射回去再开凭证，那等于信任所有网站。
  • 预检由浏览器自动发，前端代码里不要自己先写一个 OPTIONS。
  • 服务端没返回 CORS 头时，请求可能已经执行，只是脚本被浏览器拦住。改数据的接口不能靠「跨域读不到」来代替 CSRF 防护。

开发环境代理

浏览器页面和接口不同源时，让开发服务器把 /api 转到后端，浏览器只跟开发服务器同源。Vite：

webpack-dev-server 使用 devServer.proxy，字段类似。上线后由 Nginx 做同样的反向代理，或由接口自己正确返回 CORS。代理不是前端运行时的一种请求模式。

JSONP 已经不该用在新接口

<script src="https://api.example/data?callback=cb"> 不受 AJAX 同源策略约束。服务端返回 cb({...})，页面执行它。它只有 GET，并且响应会被当成脚本执行。第三方一旦被篡改，就是 XSS。新接口用 CORS。

窗口之间用 postMessage

iframe、弹窗跨源通信用 postMessage，接收方核对 event.origin。细节见《前端 iframe 通信》。document.domain 放宽同源的做法已经废弃，不要写进新代码。

Cookie 与跨站

Cookie 是否随跨站请求发送，由 SameSite、Secure 和是不是顶级导航决定，和 CORS 头无关。前端把令牌放在 Authorization 里、由本站脚本附上，第三方页面模仿不了这个头，除非令牌已经泄露。
