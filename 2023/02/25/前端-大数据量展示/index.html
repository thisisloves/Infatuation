前端 大数据量展示

2023-02-25
  • 前端
本文总阅读量次

系我一身心，负你千行泪。

先不要把十万条都交给浏览器

一次创建十万个 DOM 节点，布局和绘制都会卡住。更常见的正确顺序是：接口分页或按条件筛选，浏览器只拿当前要看的几十条。下面的实验故意让服务器返回十万条，用来对比渲染手段。它不是生产方案。生产接口应接收 page 和 pageSize，或按滚动位置返回一段。

本地用 Node 造数据即可，不必全局安装 nodemon：

演示页和接口不同源时，写明页面的源。不要用 * 再去带 Cookie。这个接口是简单 GET，不需要在每次响应里列出全部方法；若以后改成带 JSON 的 POST，再处理 OPTIONS 预检。

文本用 textContent 写入。即使用户数据看起来只是「第几号」，innerHTML 也会把内容当标记解析。

一次性渲染

循环 appendChild 十万次，每次都可能触发布局。主线程在这段时间里点不了页面。console.time 如果写在 setTimeout 之前就 timeEnd，量到的只是「安排任务」的时间，不是画完的时间。要量渲染，把结束点放进最后一批的回调里。

分批让出主线程

setTimeout(fn, 0) 把下一批放到后续任务里，浏览器有机会先画已经插入的节点、先响应点击。它不减少总工作量，十万个节点最后仍在文档里，内存和滚动仍然差。

requestAnimationFrame 把插入对齐到帧之前，同样是让出主线程，不是自动减少重排次数。重排少，是因为一批节点先进文档片段，再一次插入父节点。

最后一页的下标不要超过数组长度：

DocumentFragment 本身不会出现在页面上，插到父节点时，它的子节点被移过去。循环到 page * limit + limit 而不和 length 取最小值，最后一页会读到 undefined。

分批渲染适合「必须在本地把结果都挂上、但不要卡死首屏」的中等列表。十万行的滚动列表用虚拟列表。

虚拟列表

可视区域只能看到有限的行。虚拟列表只创建这几行，加上上下缓冲，其余用空白撑出总高度，让滚动条比例正确。

行高固定时计算最简单。假设每行 40px，容器高 400px，则可见 10 行，上下各多渲染 5 行缓冲。

容器自己 overflow: auto，并且有固定高度。滚动监听用 passive: true，避免无谓地阻止滚动。总高度用占位层撑开，可见行用 transform 挪到当前起点，不要用巨大的 padding 去挤，padding 在极端长度下并不更省。

行高不固定时，要先估算再在渲染后测量，并缓存每一行的偏移，复杂度和出错点都高一截。这种列表优先用成熟实现，自己写要补滚动条拖拽、快速滚动、窗口尺寸变化后的重算。

滚到接近底部再向接口要下一页，是分页和虚拟列表的组合：内存里只保留已加载页，DOM 里只保留可视行。不要在滚到底时把新的十万个节点追加进文档。

和页面卡顿相关的其它点

图片即使只有几十像素，十万张也会占内存。列表行里能用纯色或图标代替就不要每行一张图。过滤和排序放在取数之前，避免在主线程里对十万条做无索引的反复筛选。调试时看性能面板里的长任务，而不是只看 console.time 在调度点就结束的数字。
