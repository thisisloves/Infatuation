数组、链表和红黑树

JDK 8 及以后，HashMap 的主干是 Node<K,V>[] table。每个下标是一个桶：空、单个节点、链表，或一棵红黑树。

put 的路径可以记成五步。

  1. 表为空则按默认容量建数组。
  2. 用键算出下标，桶空就直接放。
  3. 桶里已有节点：先看头结点是不是同一个键；不是则沿链表或树查找。
  4. 找到相同键就覆盖值；找不到就追加，链表长度到阈值再考虑树化。
  5. 元素个数超过阈值就扩容。

相同键的判定是：hash 相等，并且 == 或 equals 为 true。只重写 equals、不重写 hashCode，两个内容相同的键会进不同桶，get 就找不到。

链表节点是 Node，树节点是 TreeNode。树化之后查找从 O(n) 降到 O(log n)，对付的是哈希很差、大量键挤在同一个桶里的情况。

哈希、扰动和下标

键为 null 时哈希固定为 0，所以最多一个 null 键，永远落在 0 号桶。其它键：

高 16 位与低 16 位异或，称为扰动。目的是让 hashCode 的高位也参与下标，减少低位相同造成的碰撞。容量永远是 2 的幂，下标用 hash & (n - 1)，等价于对 n 取模，但只保留低位，比除法便宜。

容量不是 2 的幂时，n - 1 的二进制不是全 1，有的位永远用不上，桶会空一截。所以构造时传入 10，实际容量会取成不小于 10 的 2 的幂，也就是 16。

容量、负载因子和扩容

量 默认 含义
容量 16 桶数组长度，始终是 2 的幂
负载因子 0.75 空间和时间的折中
阈值 容量 × 负载因子 元素个数超过它就扩容，默认 12

0.75 是经验值：再高，冲突变多，链表和树变长；再低，数组更空，扩容更勤，浪费内存。可以在构造器里改，没有特殊证据就用默认。

扩容时新容量是旧容量的 2 倍，阈值按同样比例增加。JDK 8 不再对每个键重新算哈希，只看扰动后哈希里「新增的那一位」：是 0，节点留在原下标；是 1，下标加上旧容量。链表会按这一位拆成两条，相对位置不变。

扩容要遍历旧桶并迁移节点，是 put 里最重的一步。能估计元素个数时，用 new HashMap<>(expected / 0.75 + 1) 一次分够，避免反复扩容。

为什么 8 才树化、6 才变回链表

桶里已经有 8 个节点再插入时（TREEIFY_THRESHOLD）尝试树化；扩容拆开后，某一侧节点数不超过 6（UNTREEIFY_THRESHOLD）则退回链表。8 和 6 之间留一档，避免在阈值附近来回转换。

树化还有第二个条件：数组长度至少 64（MIN_TREEIFY_CAPACITY）。长度不够时，这次冲突只触发扩容，不建树。

两个数字都有理由，面试要分开说。

泊松分布下，负载因子 0.75 时一个桶达到 8 个节点的概率已经极低。正常哈希几乎走不到树化；走到了，多半是 hashCode 写坏或被刻意碰撞。红黑树节点比链表节点大，短链表的查找也不比树差，所以阈值定在 8 而不是 3、4。

桶很长，有时是数组太短，不是哈希坏了。先把数组拉到 64，元素重新分散，多数「长链表」会消失。数组已经不小仍挤在一个桶里，再付出树节点的内存才划算。扩容时如果节点数落到 6 及以下，树会拆回链表，避免小树一直占着。

key 为 null

put(null, v) 走单独路径，哈希按 0 算，不调用 hashCode，也不会空指针。第二个 null 键会覆盖前一个。值可以任意个 null，值不参与定位。

TreeMap 在自然排序下不能用 null 键，比较器要是自己处理了 null 才行。不要把 HashMap 允许 null 的习惯带到排序 Map 上。

为什么线程不安全

HashMap 没有锁，也没有用 CAS 保护结构。两个线程同时改同一张表，至少有三类问题。

  • 丢失更新：两个线程都看到同一个空桶，各自 new 一个节点再写回数组，后写的覆盖先写的，先放入的键消失。
  • size 不准：个数用普通读写累加，并发 put 会丢掉增量，阈值判断跟着错。
  • 结构被写坏：一个线程正在扩容、迁移链表，另一个线程同时 put 或 get。JDK 7 的头插法在并发扩容时可能把链表收成环，get 死循环；JDK 8 改成尾插，环基本消失，但丢失更新、读到一半的树、扩容与写入交错仍然在。

所以「JDK 8 不会死循环」不等于线程安全。多线程读写同一张 HashMap 的结果是未定义行为。只读共享、初始化之后不再改，可以靠安全发布让别的线程看见完整引用；只要还有写入，就不要共用。

和 ConcurrentHashMap 比

HashMap ConcurrentHashMap
并发 不安全 分段演进为桶级锁 + CAS，读一般不加锁
null 键和值都允许 键和值都不允许，null 用来表示「没有」
计数 普通字段 baseCount 加 CounterCell，减少竞争
迭代 fail-fast，结构被改就抛异常 弱一致，不抛 ConcurrentModificationException，也不保证看到最新写入
锁粒度 无 只锁正在写的桶，扩容时多线程可以帮忙迁移

JDK 8 的 ConcurrentHashMap 去掉了分段锁。空桶用 CAS 放入头结点；冲突时只对这个桶的头结点 synchronized。树化阈值同样是 8，但并发容器里树的旋转还要照顾别的线程正在读。

计数、contains 这类复合动作用 HashMap 时要在外面自己加锁，检查和写入之间仍有空档。ConcurrentHashMap 提供 putIfAbsent、compute、merge，把「先看再写」收成一次原子操作。需要这个语义时用它，不要在 HashMap 外包一把大锁冒充。
