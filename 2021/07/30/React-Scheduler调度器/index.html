React Scheduler 调度器

2021-07-30
  • React
本文总阅读量次

他生莫作有情痴，人间无地著相思

它排的是什么

Scheduler 不负责 Diff，也不改 DOM。它只回答两件事：众多更新里先做哪一件，以及当前这段 JavaScript 还能不能继续占着主线程。

Reconciler 在 render 阶段给节点打 flags。Renderer 在 commit 阶段落地。React 15 没有这一层，更新只能同步做完。

事件循环里真正的顺序

把「每个宏任务后面必有 rAF、重绘、requestIdleCallback」连成一条固定流水线，和规范不符。更接近实现的模型是：

  1. 从某个任务队列取出 一个 宏任务并执行。setTimeout、事件回调、MessageChannel 的 onmessage 都是宏任务。
  2. 执行完立刻清空 微任务（Promise.then、queueMicrotask、MutationObserver），直到队列空。微任务里再排队微任务，会在绘制前全部跑完。
  3. 不一定绘制。浏览器大约按刷新率寻找渲染机会（页面在前台时常见约 16.7ms 一次）。有机会时才跑 requestAnimationFrame，接着样式、布局、绘制。
  4. 这一帧如果还剩时间，才可能跑 requestIdleCallback。它不是每轮循环的固定一步。

因此：微任务插在绘制之前；rAF 属于渲染步骤，不是每个宏任务的下一站；requestIdleCallback 是「绘制之后的剩余空闲」，不是 React 的调度器。

React 实际怎么切片

scheduler 包（React 16 后期就在用，并不只到 React 17 才出现）的宿主回调是 MessageChannel：

  • port.postMessage 把 performWorkUntilDeadline 排进宏任务，没有 setTimeout 嵌套时的 4ms 钳制。
  • 回调里取出到期任务执行。
  • shouldYieldToHost() 比较 now - startTime 和 frameInterval。默认 frameInterval 是 5。forceFrameRate(fps) 把它改成 Math.floor(1000 / fps)。
  • 时间片用完还有任务，就再 postMessage 一次，把剩余工作让到后面的宏任务。浏览器因此有机会在两个切片之间绘制。

这和 requestIdleCallback 的差别是：React 自己制造宏任务，不等浏览器宣布空闲。页面正在忙时，过渡更新仍能一点点推进，只是经常让出。

并发协调侧：

shouldYield() 为真只是暂停 render 阶段。commit 不会走进这个循环。

过期时间与两个堆

Scheduler 的每个任务带 expirationTime 和 priorityLevel。优先级越高，超时越短，例如用户阻塞优先级大约 250ms 量级，普通优先级大约数秒，Idle 几乎不过期（具体毫秒数以当前 scheduler 源码为准，会微调）。

  • 还没到开始时间的任务在 timerQueue。
  • 已经可以执行的任务在 taskQueue。
  • 两者都是最小堆，堆顶是过期时间最近的任务。

先把 timerQueue 里到期的挪到 taskQueue，再取 taskQueue 的堆顶。过期任务会被尽量做完，避免低优先级更新永远饿死。

五个优先级：ImmediatePriority、UserBlockingPriority、NormalPriority、LowPriority、IdlePriority。协调器里的 Lane 是另一套位图，用来表达「一批同优先级更新」和「打断后续算」，不要和这五个枚举当成同一份常量。

和应用代码的边界

业务里不要模拟时间片，也不要调 scheduleCallback。需要把大更新标成可延后，用 startTransition 或 useDeferredValue。需要这次更新在继续往下执行前就画上屏幕，用 flushSync，它走同步车道，不参与让出。
