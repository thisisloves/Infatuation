React Fiber

2021-06-12
  • React
本文总阅读量次

泪眼问花花不语，乱红飞过秋千去。

Fiber 要解决的问题

React 15 的 Stack Reconciler 用递归对比整棵树。递归一旦开始，JavaScript 主线程就停不下来，输入、动画和绘制都要排队。节点一多，一次更新超过一帧，页面掉帧。

Fiber 是 React 16 引入、一直用到 React 18 / 19 的协调架构。它做两件事：

  1. 把递归改成可以暂停的循环，每个单元是一个 Fiber 节点。
  2. 给更新标优先级。紧急更新可以插队；低优先级更新做了一半可以丢掉重来。

时间分片只在并发渲染里生效。ReactDOM.render（legacy）虽然也走 Fiber 数据结构，但 render 阶段走 workLoopSync，中途不让出。createRoot 之后，过渡更新才走 workLoopConcurrent，用 shouldYield() 决定要不要把主线程还回去。

和浏览器主线程的关系

布局、绘制和大部分 JavaScript 都在主线程上排队，所以长时间同步 JS 会推迟绘制。合成器线程可以独立处理部分 transform / opacity，但 React 改 DOM 结构、读布局，仍然占主线程。

一帧大约 16.7ms（60Hz）。React 的 Scheduler 不会把整帧都拿来跑协调。默认时间片大约 5ms（frameInterval），到点就让出，把绘制机会留在这一帧里。把「必须在 16.7ms 内做完整棵树」理解成 Fiber 的切片长度，是把帧预算和 yield 间隔混在一起了。

合作式调度，不是抢占

浏览器没有抢占式中断 JS 的能力。Fiber 是合作式的：做完一个节点，主动问 Scheduler 时间片是否用完、有没有更急的更新。有就停；没有就处理下一个节点。

可中断的是 render 阶段（beginWork / completeWork，在内存里算）。commit 阶段改 DOM、跑 useLayoutEffect 和 componentDidMount / componentDidUpdate，一旦开始就不会让出，否则用户会看到改了一半的界面。

Fiber 是节点，也是工作单元

每个组件、DOM 节点、文本节点在内存里对应一个 Fiber。子节点用 child 指向第一个孩子，孩子之间用 sibling 串成单链表，return 指回父节点。遍历可以写成循环：先深入 child，没有 child 就走向 sibling，再没有就沿 return 回到父节点。循环比递归容易在任意节点停下来。

已经删除的 effect 链表

React 16 在 complete 阶段把有副作用的节点用 firstEffect / nextEffect / lastEffect 串成 effectList，commit 时只走这条链表。React 17 起这条链表被拿掉，副作用改记在 flags 和 subtreeFlags 上，commit 深度优先走树，遇到 subtreeFlags === NoFlags 就跳过整棵子树。再把 nextEffect 写成现行数据结构，是 React 16 的记忆。

优先级名字也换过

早期演讲里的 synchronous / task / animation / high / low / offscreen，不是现在的公开模型。Scheduler 包的优先级是：

  1. ImmediatePriority
  2. UserBlockingPriority
  3. NormalPriority
  4. LowPriority
  5. IdlePriority

协调器内部再映射成 Lane（见《React Lane 模型》）。OffscreenLane 是给隐藏子树用的车道，不是 Scheduler 的一个叫 offscreen 的优先级。

一次更新怎么走

  1. setState、createRoot().render()、flushSync 等创建 update，按车道挂到 Fiber 的 updateQueue。
  2. Scheduler 按优先级和过期时间挑选任务。过期的进 taskQueue，还没到期的进 timerQueue，两个都是按时间排序的最小堆。
  3. 有时间片时从根开始建 workInProgress 树。并发渲染里 shouldYield() 为真就停，下次从当前 Fiber 继续，或因更高优先级而整棵重做。
  4. render 阶段结束得到一棵完成的 WIP 树。commit 根据 flags / subtreeFlags 改 DOM。
  5. commit 之后 WIP 变成 root.current。useEffect 的被动副作用在绘制之后再跑。

这里没有 requestIdleCallback。早期设计考虑过它，正式实现不用：它要等浏览器自认为空闲，忙的时候更新会饿死；默认 deadline 约 50ms，对 60fps 太粗；触发也不稳定。React 用 MessageChannel 把「继续干活」排成宏任务，自己用 performance.now() 判断 5ms 时间片，而不是等空闲回调。

为什么旧生命周期被标成 UNSAFE

render 阶段可能执行多次、做到一半被丢掉。componentWillMount、componentWillReceiveProps、componentWillUpdate 若在这里发请求、改外部变量，就会重复。它们被改名为 UNSAFE_*。副作用放到 commit 之后：componentDidMount、componentDidUpdate、useEffect。渲染期间要算状态，用纯函数 getDerivedStateFromProps。

和双缓存的关系

更新不直接改屏幕上那棵 current 树。另一棵 workInProgress 通过 alternate 和 current 成对。commit 时一次换成新树。细节见《React 双缓存》。
