愿你有前进一寸的勇气，亦有退后一尺的从容。

Provider 把 store 放进 context

react-redux 的 Provider 使用 React context。子组件用 Hooks 或 connect 读取。store 不要每次渲染都新建，否则订阅会全部重来，状态回到初始值。

React 18 请使用 createRoot。react-redux 7 起配合 React 18 的批处理；版本过旧时，一次 dispatch 可能让多个 useSelector 各渲染一次。升级 react-redux 到与 React 18 匹配的主版本，而不是在每个回调里手写 unstable_batchedUpdates。

useSelector 与 useDispatch

选择函数应返回原始值或稳定引用。默认比较是 Object.is。需要浅比较时：

如果 items 数组本身在 reducer 里是新引用，浅比较也拦不住，这是对的：列表变了就该渲染。浅比较解决的是「你在 selector 里组装了新对象，但字段没变」。

selector 里不要 dispatch。渲染期间改 store 会嵌套更新。派生数据算完返回即可。

connect 仍然可用

mapStateToProps 返回的对象会浅比较。mapDispatchToProps 传对象时，每个 action creator 会绑上 dispatch。传函数时，签名是 (dispatch, ownProps) => ({ ... })，ownProps 是组件自己的 props。

ownProps 变化会重新调用 mapStateToProps。不要在里面 filter 大数组却不记忆，父组件一渲染就会重算。Hooks 写法把过滤放在 useMemo 或 reselect 里，依赖更显眼。

多个 store 与自定义 context

测试或微前端里若真有第二个 store，使用 <Provider context={MyContext} store={store}>，Hooks 用 createDispatchHook(MyContext)。默认 context 只有一个，两个 Provider 嵌套时内层遮蔽外层，不是合并。

性能

  • 一个大组件订阅整棵 state，任何 action 都会让它渲染。拆成小组件，各自选择自己的字段。
  • 列表项订阅 state.todos.entities[id]，而不是订阅整个 todos 再在项里查找。配合规范化的 state，一项变化不会渲染其他项。
  • connect 的函数组件默认不因父组件渲染而跳过。需要时包 React.memo，并保证父组件传入的其余 props 稳定。

store 的更新是同步通知订阅者的。过渡更新若希望不挡住输入，把重渲染的那部分放进组件的 startTransition，Redux 本身没有车道。不要为了「Redux 异步」去包一层 setTimeout 再 dispatch，那样只是把渲染推迟到下一个宏任务，顺序更难想。
