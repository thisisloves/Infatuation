Git 分支管理

2018-08-19
  • Git
本文总阅读量次

明月楼高休独倚，酒入愁肠，化作相思泪。

分支是可移动的指针

分支用来在主线之外改代码。Git 里新建分支只是增加一个指向当前提交的引用，切换时改 HEAD 并检出那棵树，所以成本很低。提交历史是有向图，分支名只是贴在某个提交上的标签，不是一份单独的文件副本。

默认分支名随版本和平台变化。新仓库可以用 git config --global init.defaultBranch main，已有仓库以远程的默认分支为准。main 和 master 没有功能差别。

删除远程分支是推送一个空源：git push origin --delete dev。本地的 origin/dev 要下次 git fetch --prune 才消失。只删本地分支，远程那一支还在。

快进和合并提交

主线没有新提交、还是 dev 的祖先时，git merge dev 只把指针快进，历史仍是一条直线。两边都有新提交时，Git 生成一次有两个父提交的合并。想在任何时候都留下合并节点，用 git merge --no-ff dev。

功能分支上的提交还没公开、希望接到主线顶端时，可以先在功能分支上 git rebase main，再快进合并。变基会改写被重放的那些提交的哈希。已经推送且有人基于它开发时，不要变基这条共享分支。

常见分支模型

  1. **main / master**：可发布的线。许多团队用 main 作为默认分支。
  2. **develop**：日常集成。小团队可以不设，直接从 main 拉功能分支。
  3. **feature/***：单个功能，做完合并后删除。
  4. **release/***：从开发线拉出准备发布，只收修复，完成后合并回发布线并打 tag。
  5. **hotfix/***：从生产分支拉出的紧急修复，修完同时合并回生产线和当前开发线。

这是一种约定，不是 Git 内置的五种类型。只有 main 和短期功能分支也可以工作。

协作约定（示例）

  1. main 与需要共享的 develop 放在远程。短期 feature 可以只留在本地，合并后删除。
  2. 进入生产分支走合并请求，避免在 main 上直接堆未审查的提交。
  3. 线上故障从对应的生产提交拉 hotfix，修完合并回 main 和 develop。只合并回一条线，另一条线以后会丢这次修复。
  4. 预发布上的缺陷，在所属的 feature 或 release 上修，再逐级合并。
  5. 长期并行的两条版本线用不同分支名（如 release-1.1 与 release-1.2），避免在同一个分支上来回检出。

常见坑

  • 工作区有未提交修改时切换分支，若目标分支也改了同一文件，Git 会拒绝切换。先提交、git stash 或丢掉修改。未改到的文件可以带着走。
  • 本地 main 和 origin/main 分叉时，git push 被拒绝。先 git pull --rebase 或合并，再推。
  • git branch -d 说未合并，就用 git log main..dev 看那些提交还要不要。要，就先合并；不要，再用 -D。
  • 跟踪关系在 git push -u、克隆、或 git switch 到已有远程分支时建立。没有上游时，git status 不会显示领先或落后多少。
