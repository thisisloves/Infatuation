Git 冲突解决

2018-08-10
  • Git
本文总阅读量次

多少红颜悴，多少相思碎，唯留血染墨香哭乱冢。

冲突从哪来

合并或变基时，双方改了同一文件的相邻行，Git 无法自动选出一份结果，就会停下来要人裁决。只在一边改过的文件会自己合上；两边改的区域隔得够开，也会自动合成一份。

典型场景：本地分支和它的上游都有新提交，git pull 或 git merge 停下，git status 列出 unmerged paths。

标记长什么样

合并时，<<<<<<< HEAD 到 ======= 是当前分支（ours），下面到 >>>>>>> 是被合并进来的分支（theirs）。

变基时两侧对调：正在重放的提交被标成 theirs，新基底被标成 ours。因为变基时 HEAD 已经站在新基底上，正在重放的那次提交是「拿进来的」。按标记里的分支名读，比死记 ours/theirs 不容易选反。

裁决后删掉所有标记，文件里只留最终内容。标记留在文件里再提交，等于把冲突符号写进了仓库。

冲突期间，索引里同一路径有三级：:1: 是共同祖先，:2: 是 ours，:3: 是 theirs。

处理步骤

合并冲突用 git commit 收尾，Git 会带上两个父提交。不要在这时改成一次普通的单父提交，除非确实打算丢掉合并结构。变基或 cherry-pick 用对应的 --continue 结束这一次重放。只 git commit、忘了 --continue，会停在变基或拣选的中途：

常见坑

  • 二进制文件、生成物和锁文件冲突时，Git 给不出有意义的行合并。选定一侧：git checkout --ours -- <file> 或 --theirs，再 git add。变基过程中 ours/theirs 与合并相反。拿不准时用 :2:、:3: 看内容，不要按单词猜。
  • 两边都改了文件末尾却没有换行，或行尾 LF / CRLF 不一致，会整文件冲突。统一 .gitattributes 里的 eol，比在每次合并里手改换行可靠。
  • 冲突未加进暂存区就 git commit，Git 会拒绝结束这次合并。git add 表示这个文件已经裁决完。提交前搜一下 <<<<<<<，避免标记残留。
  • 已经推送的共享分支上，解决冲突用新的合并提交，或在个人分支上变基后推送。不要对别人正在基于的历史做强推。
