Git 版本回退

2018-09-26
  • Git
本文总阅读量次

十年不到香雪海，梅花忆我我忆梅。

先看改动停在哪一层

  1. 只改了工作区，还没 git add。
  2. 已经暂存，还没提交。
  3. 已经在本地提交，还没推送。
  4. 已经推到远程，别人可能基于它继续提交。

前三层可以移动指针或还原文件。已经公开的历史优先用 git revert 追加反向提交。reset 后再强推会让别人的后续提交失去基点。

工作区：丢掉未暂存的修改

git restore <file> 默认用暂存区覆盖工作区。文件已经 add 过又在工作区改过时，这条会回到暂存的那一版，而不是最近一次提交。

只加 --source=HEAD 时，改的是工作区，暂存区不动。暂存区里若还留着上一次 add，状态会变成「已暂存的内容和工作区不一致」。工作区和暂存区都要回到这次提交：

未跟踪的新文件不在提交里，restore 不会删它。确认无用后删除文件，或 git clean -n 预览再 git clean -f。-fd 会连未跟踪的目录一起删，reflog 找不回从未提交的文件。

只要某个历史文件、而不是整库回退时：

暂存区：取消 add

这一步只把暂存区退回 HEAD，工作区里的修改还在。若连工作区也要丢掉，再用上一节同时指定 --staged 和 --worktree 的写法。

本地提交：reset 的三种模式

模式 HEAD 暂存区 工作区
--soft 移到目标 保留，目标之后的改动仍暂存 不动
--mixed 移到目标 改回目标提交 工作区保留那些改动
--hard 移到目标 改回目标提交 工作区也改回目标提交

--soft 适合把最近几次提交拆开或合成一次，改动还都在暂存区里。--hard 会丢掉目标之后尚未另存的修改。执行前确认 git status 是干净的，或这些修改可以不要。

HEAD~2 沿第一父提交向上两代。HEAD^2 是当前这次提交的第二父提交，只有合并提交才有。~ 和 ^ 不是同一件事，不能把「向上两步」写成 HEAD^2。

已推送：用 revert

revert 生成一次新提交，内容与目标提交的差异相反。历史不被改写，别人已经拉走的提交仍然有效。范围要写成从更旧的那一次到更新的那一次；写反了，A..B 里没有提交。中间有合并提交时加 -m 1，1 一般是合并发生时所在分支，也就是第一父提交。

后悔 reset 之后

分支指针移走后，提交对象通常还在，一段时间内能从引用日志找回来：

reflog 在本地，不会跟着 push 走。过期被回收之后，就无法再靠它找回。必须改写已经推送的历史时，用 git push --force-with-lease。它会在远程和你上次见到的位置不一致时拒绝推送，避免盖掉别人刚推上去的提交。团队需要事先知道这条分支将要改写。

常见坑

  • git reset --hard 与 git clean -fd 叠在一起时，未跟踪的目录也会被删掉。
  • 修改最近一次尚未推送的说明，可以用 git commit --amend。amend 同样生成新哈希。已经推送后再 amend，等于改写公开历史。
  • 检出历史提交而不建分支会进入分离 HEAD。接着提交时，那些提交不挂在任何分支上，一切换就只能靠 reflog 找回。要在旧提交上改，先 git switch -c fix <commit>。
