Git 遴选（cherry-pick）

2018-10-05
  • Git
本文总阅读量次

心静闲看物亦静，芭蕉过雨绿生凉。

cherry-pick 做什么

  • cherry-pick 把某一次或若干次已有提交的改动应用到当前分支，生成新提交。新提交的哈希、作者时间与父提交都和原来不同，原提交留在原分支上。
  • 适合把热修从维护分支拣回主干，或从一长串试验提交里只取其中一两个。要整段历史的关系时，用合并或变基，而不是逐个拣。

和 merge、rebase 的差别

  • merge 把另一分支的提交接进来，并留下一个带两个父提交的合并节点（快进时除外）。
  • rebase 把当前分支上的一段提交按顺序重放到新基底上，这段历史的哈希都会变。
  • cherry-pick 不要求两条分支有合并关系，可以跳过中间提交，也可以跨仓库拣同一对象库里能看到的哈希。

拣一个提交

  • 当前工作区要干净，或至少和将要改的文件不重叠。否则 Git 会拒绝开始。
  • -x 在说明末尾记下来源哈希，以后还能查这行改动从哪次提交来。从私有分支拣到公开分支时，这条来源地址可能指向别人访问不了的提交，这种场合可以不加 -x。
  • -n（--no-commit）只把改动放进暂存区，不立刻提交，便于和本地修改揉成一次提交。

多个提交

  • 列出多个哈希时，从左到右依次应用，中间被跳过的提交不会自动补上：
  • 两点范围 A..B 是「从 B 能走到、从 A 不能走到」的提交，不含 A、含 B，并按提交时间从旧到新应用。A 必须是 B 的祖先，这段范围才是两人之间的直线历史：
  • 要连 A 自己也拣，写成 <commitA>^..<commitB>。A 是根提交、没有父提交时，这个写法不成立，改为单独写出 A 的哈希。

冲突、空提交与合并提交

  • 原提交若只改了当前分支已经有的那些行，拣选结果可能是空的。默认会停下来；确认不需要这次提交时用 --skip。
  • 合并提交有两个父提交，必须用 -m 1 或 -m 2 指定相对哪一个父提交来计算差异。拣错父提交，补丁方向会反。能用合并解决的，不要把合并提交再 cherry-pick 一遍。

常见坑

  • 同一改动拣两次，第二次会在相同行上冲突，或生成重复逻辑。拣之前用 git log --grep 或看来源说明，确认主干里还没有它。
  • 拣选不搬运原提交的下游。A 修了接口、B 的调用依赖 A 时，只拣 B 会编不过。范围要包含它所依赖的那些提交。
  • 已经推送的分支上，别人若基于旧提交继续开发，你在本地对那些提交做 cherry-pick 不会改写他们的历史；改写要发生，得是你对他们正在用的分支做了变基并强推。
  • 拣完用 git log --oneline 核对顺序。范围的应用顺序是从旧到新，和 git log 默认从新到旧的显示相反。

拣选之前先看差异

  • git show 看这次提交动了哪些文件。一次提交里夹着不该带上主干的调试代码时，用 git cherry-pick -n，在暂存区里改完再提交。
  • main..feature 列出功能分支上主干还没有的提交。从中挑选哈希，比在图形界面里抄错一位再拣到无关提交安全。
  • 拣选上来的新提交可以用 git log -1 --format=%B 看说明。加了 -x 时，正文末尾有 (cherry picked from commit ...)。

已拣上主干之后

  • 功能分支若稍后还要整个合并进主干，那些拣过的提交可能再次冲突，因为同样的行改了两次。主干上的拣选提交若带 -x，合并时更容易认出重复。
  • 也可以在功能分支合并之后删掉单独的拣选，只保留合并节点。热修要先上生产、功能分支还不能合并时，拣选是合理的中间步骤，事后把热修分支合并回功能分支，避免两处各改各的。
  • 热修从生产分支拉出，合并回生产分支和开发分支各一次。若只 cherry-pick 到一边，另一边以后仍会缺这行修复。
