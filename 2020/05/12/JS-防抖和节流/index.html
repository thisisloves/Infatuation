JS 防抖和节流

2020-05-12
  • JS
本文总阅读量次

适度的温婉就是温柔，温柔不是示弱，不是妥协，只是真诚，善良，在安静中不慌不忙的坚强。

概念

两者都用来降低高频事件的处理次数，语义不同。

  • 防抖（debounce）：每次触发都把执行推迟 delay 毫秒。期间再次触发就重新计时。适合「停下来再做」，例如输入停止后再请求搜索。连续输入时，前面的调用不会执行。
  • 节流（throttle）：每个时间窗最多执行一次。适合滚动、缩放、拖拽这类持续事件，既要跟手，又不能每帧都打接口。

「单位时间内只执行一次」只对节流始终成立。防抖在不停触发时一次都不执行，安静下来才执行那一次。

正确示例

尾部防抖：停手后执行最后一次，并保留 this 和参数。

时间戳节流：窗口起点立即执行，窗口内的后续触发丢掉。

滚动加载更适合节流；搜索框更适合防抖。若既要第一次立刻响应、又要结束时补一次，可以在节流里同时记定时器做尾调用，那是另一种变体，不要和上面的头部节流混为一谈。

常见坑

  • 把定时器 id 存在 fn.id 上会改掉原函数。同一个 fn 被包装两次时互相 clearTimeout。定时器放在闭包里的 let timer。
  • fn.apply(null, args) 把 this 固定成 null。方法作为回调时要用包装函数自己的 this。
  • keyup 防抖搜索会漏掉鼠标粘贴后不松键的情况，监听 input 更完整。
  • 组件卸载后，防抖定时器仍可能触发 setState。返回带 cancel 的函数，在卸载时 clearTimeout。
  • 滚动监听即使用了节流，也应 { passive: true }，避免无谓地阻塞滚动。每帧跟手的动画用 requestAnimationFrame，不必再套一层 200ms 节流。
  • 第一次需要立即执行的按钮（防止连点）用头部节流或直接禁用按钮。尾部防抖会让用户觉得点击没反应。

选择哪一种

场景 选择 原因
搜索框停止输入后再请求 尾部防抖 连续按键只保留最后一次
按钮防止连点，且要立刻生效 头部节流或直接禁用按钮 尾部防抖会让第一次点击也延迟
滚动加载、窗口缩放 节流 过程中也要定期执行
跟手的拖拽坐标 requestAnimationFrame 和刷新对齐，比固定 100ms 更合适

两种包装都应提供取消：

页面卸载时调用 wrapped.cancel()，避免定时器在节点消失后仍去读 input.value。节流若采用时间戳，卸载时没有定时器可清，但要卸掉滚动监听本身。不要把等待时间写进业务函数里再用 Date.now 到处判断，包装一次即可。

定时器放在闭包里，避免写到函数的属性上。组件消失时调用 cancel：

搜索框用这段尾部防抖。滚动用节流，并且监听使用 passive: true。连点按钮要立刻响应时用头部节流，或在请求未完成前直接禁用按钮。

小结

防抖合并成安静后的一次，节流保证时间窗内至多一次。定时器放进闭包，this 用 apply 传回去。搜索用防抖，滚动用节流。
