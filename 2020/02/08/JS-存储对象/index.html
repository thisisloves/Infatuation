概念

Web Storage 是同源页面在浏览器里存字符串的 API，不会随 HTTP 请求自动发给服务器，这一点和 Cookie 相反。它包括：

  • localStorage：没有过期时间，同源的标签页共享，关掉浏览器还在，直到脚本 removeItem / clear，或用户清站点数据。
  • sessionStorage：按「顶级浏览上下文」隔离。同一标签里刷新还在；新开标签、复制链接到另一个标签，是另一份数据；关掉该标签即销毁。

两者接口相同，值只能是字符串。容量由浏览器按源限制，常见数量级是数 MB，超出 setItem 抛 QuotaExceededError。key(n) 的 n 从 0 开始，顺序是实现列出的键顺序，不要当成稳定的业务排序。

方法 作用
setItem(key, value) 写入；键已存在则覆盖。value 会被转成字符串
getItem(key) 读取；没有该键时返回 null，不是 undefined
removeItem(key) 删除一个键
clear() 清空当前存储对象
key(index) 按下标取键名

对象要自己 JSON.stringify / JSON.parse。undefined、函数、Symbol 键不会按对象语义保留。

常见坑

  • setItem('n', 1) 再读出来是 '1'。判断是否登录不要写 getItem('ok') === true。
  • getItem 缺失返回 null。JSON.parse(null) 得到 null 而不抛错，JSON.parse 空字符串会抛 SyntaxError。
  • 隐私模式、配额用尽、或某些嵌入环境禁用存储时，读写都会抛错，需要 try/catch。
  • sessionStorage 不是「所有窗口共享的会话」。同站新标签页看不到另一页的 session 数据。
  • Storage 没有服务端的 HttpOnly，页面里的脚本都能读。不要放令牌或密码；令牌更适合 HttpOnly Cookie。
  • 它不替代 IndexedDB。大量结构化数据、二进制、需要索引和事务时用 IndexedDB。Web SQL 已废弃。

和 Cookie、IndexedDB

Cookie 会跟请求走，适合会话标识；Web Storage 适合只在页面里用的偏好、草稿。需要索引、事务或二进制时用 IndexedDB，它按源隔离，空间由配额限制，不是无限大。Web SQL 已废弃。

隔离范围也不一样。Cookie 可以用 Domain 在父域和子域之间共享，并用 Path 限制路径。localStorage 只认源（协议 + 主机 + 端口）：https://a.example.com 和 https://b.example.com 互不可见，同一主机下不同路径反而共享同一份存储。不要用 Storage 去模拟「这个目录一份 Cookie」。

storage 事件只在其他同源浏览上下文修改 localStorage 时派发。本页 setItem 不会通知自己。sessionStorage 一般不在标签之间同步，不要用它做多标签通信。

键和值都会被转成字符串。setItem('ok', false) 存的是 'false'，它是非空字符串，当布尔用会变成真。删除用 removeItem，把值设成空字符串并没有删除键，getItem 得到 '' 而不是 null。

setItem 可能抛 QuotaExceededError。捕获后清掉可以再生的缓存，不要把用户正在编辑的草稿一起 clear()。Safari 无痕模式曾经把配额设得很小，甚至一写入就抛错，所以「支持 localStorage」不等于「一定写得进去」。

键名加前缀，例如 app:draft，避免同一源上的多个项目互相覆盖。key(i) 只适合调试，业务读取一律 getItem。

写入可能超过配额，调用放在 try 里。读到的字符串在 JSON.parse 前要允许它损坏：用户清过一半数据，或旧版本写过别的格式。

sessionStorage 在刷新后还在，复制出一个新标签则是另一份。多标签同步只用 localStorage 的 storage 事件。

小结

localStorage 持久且同源共享，sessionStorage 限当前标签。只存字符串，对象要 JSON 序列化，读不到是 null。它不上请求头，也不适合存放秘密。
