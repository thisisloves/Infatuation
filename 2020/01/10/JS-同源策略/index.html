JS 同源策略

2020-01-10
  • JS
本文总阅读量次

世事短如春梦，人情薄似秋云。不须计较苦劳心，万事原来有命。

概念

同源策略是浏览器隔离不同网站脚本的基本规则。源（origin）由三部分组成：协议、主机、端口。https://a.com 和 http://a.com、https://a.com:8443 都不同源。默认端口写不写都算同一个（https 443，http 80）。

这和 Windows 域、活动目录无关。网页里的「域」指的是这个源，不是局域网里要建立信任关系的域控制器。

同源脚本可以读本源的 DOM、document.cookie（非 HttpOnly）、Web Storage。跨源时浏览器限制的是读取，不是「任何请求都不准发」：

  • <img>、<script>、<link>、表单提交可以发起跨源请求，但页面读不到响应正文。
  • XMLHttpRequest / fetch 可以发出跨源请求；没有 CORS 许可时，脚本读 response 会失败。
  • 不能访问另一个源的 iframe DOM，存储也按源隔离。IndexedDB 同样受源限制（名字是 IndexedDB，不是 indexDB）。

正确示例

合法的跨源手段：

  1. CORS：服务端对允许的源返回 Access-Control-Allow-Origin。带自定义头或 Content-Type: application/json 的请求会先发 OPTIONS 预检。要带 Cookie 时，前端 credentials: 'include'，服务端不能把允许源写成 *，还要 Access-Control-Allow-Credentials: true。
  1. JSONP：利用 <script> 不受 CORS 约束，服务端按约定的回调名返回 callback(data)。只适用于 GET，而且服务端必须配合。现代接口应使用 CORS，不要再新写 JSONP。
  1. postMessage：跨源窗口通信。监听时检查 event.origin。

document.domain 降域只能放宽同一父域下的子域，而且正在被浏览器移除，不要用。

常见坑

  • 「跨源就不能发 Ajax」不成立。请求往往已经发出，失败的是脚本读结果。看网络面板能看到状态码，控制台仍报 CORS。
  • JSONP 若只拼时间戳、不把回调名告诉服务端，页面上的函数永远不会被调用。<script> 也没有办法做 POST，响应会被当成脚本执行，存在 XSS 风险。
  • Cookie 另有 SameSite。Lax / Strict 会在跨站请求里不带 Cookie，即使用了 CORS credentials。
  • 反向代理（开发服务器把 /api 转到后端）让浏览器认为仍是同源，这是开发期绕开 CORS 的办法，不是浏览器取消了同源策略。
  • iframe 拼写不是 ifream。跨源框架用 postMessage，不要读 contentDocument。

预检和代理

非简单请求会先发 OPTIONS。触发条件包括方法不是 GET/HEAD/POST，或带了 Authorization、Content-Type: application/json 这类非简单头。预检要允许的方法、头和源都写在响应里，否则真正的 POST 不会被脚本读到。浏览器可以按 Access-Control-Max-Age 缓存预检。

开发服务器把 /api 代理到另一台机器时，浏览器看到的仍是页面自己的源，于是没有 CORS。这只说明请求没跨源，不是同源策略失效。上线后若前端域名和 API 域名不同，代理要配在网关，或由 API 返回 CORS 头。

Cookie 的 SameSite=Lax 是默认倾向。跨站的 fetch 即使 credentials: 'include' 且 CORS 允许凭证，SameSite 仍可能把 Cookie 留在家里。会话要跨站携带时才使用 SameSite=None; Secure，并确认接口不是任意网站都能带上凭证调用。

postMessage 的第二个参数必须是具体源，不要写 * 再在监听里不检查 event.origin。校验失败就丢弃消息。

脚本、图片和画布

<script src> 可以加载跨源脚本并执行，但页面读不到脚本文件的源码。<img> 可以显示跨源图片，把这张图画进 Canvas 再 getImageData 会污染画布并抛安全错误，除非图片响应带了合适的 CORS 且元素设置了 crossOrigin。

这仍要求 CDN 返回 Access-Control-Allow-Origin。没有这个头，图片能看，像素读不出。

窗口之间只共享同源的 localStorage。https://a.com 和 https://a.com:8443 端口不同，存储不共享，iframe 的 contentDocument 也读不到。这种页面用 postMessage，并核对 event.origin 的协议、主机和端口三部分。JSONP 只作为理解旧接口的例子，新接口用 CORS。

简单请求和凭证

「简单请求」大致是 GET、HEAD、POST，且头和 Content-Type 落在旧表单允许的范围内（如 text/plain、application/x-www-form-urlencoded、multipart/form-data）。这种请求可能不预检，但脚本要读响应，仍然需要 Access-Control-Allow-Origin。没有这个头时，网络面板里看得到 200，fetch 的 Promise 仍会拒绝。

mode: 'no-cors' 得到的是不透明响应，status 为 0，正文读不出，只能用来触发缓存或埋点，不能拿来解析 JSON。要 Cookie 就同时设置 credentials: 'include' 和服务端的凭证头，允许的源必须是具体域名。

iframe 的跨源限制同样作用在 contentWindow.document。父页面改子页面样式做不到时，把样式放进子页面，或只通过 postMessage 传数据让子页面自己改。

小结

源 = 协议 + 主机 + 端口。同源策略限制的是跨源读取和 DOM/存储访问。跨源读接口用 CORS，跨窗口用 postMessage，不要把 Windows 域或「Ajax 完全发不出去」写进结论。
