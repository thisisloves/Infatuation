JS 缓存优化

2020-04-04
  • JS
本文总阅读量次

入我相思门，知我相思苦，长相思兮长相忆，短相思兮无穷极。

概念

HTTP 缓存是浏览器按响应头决定要不要重新下载资源。它和前进、后退使用的往返缓存（bfcache）不是一回事：bfcache 冻结整页，HTTP 缓存保存的是单个响应。

查找时先问强缓存是否新鲜。新鲜就不再发请求，开发者工具里常见 200 (from disk cache) 或 memory cache。不新鲜、或者头要求必须再验证，才发条件请求，这就是协商缓存。顺序是「先本地新鲜度，再问服务器」，不是先服务器。

强缓存：

  • Expires（HTTP/1.0）：绝对 GMT 时间。客户端改了系统时钟就会判错。两边都有时，Cache-Control 优先。它没有被从协议里删掉。
  • Cache-Control（HTTP/1.1）：max-age=3600 表示响应生成后的 3600 秒内视为新鲜（还要扣掉 Age）。public 允许共享缓存，private 只允许浏览器。no-cache 是可以存，但用之前必须向服务器验证，不是禁用缓存。no-store 才是不要存储。

协商缓存返回 304 时没有正文，浏览器继续用本地副本；资源变了才是 200 加新正文。验证器两对：ETag / If-None-Match 优先于 Last-Modified / If-Modified-Since。Last-Modified 精度到秒，同一秒内的修改可能被漏掉。

Service Worker 可以在网络之前回答，属于你写的缓存策略（Cache Storage），优先级和 HTTP 缓存头不是同一层。Chrome 曾经的 Memory Cache、Disk Cache 是 HTTP 缓存的存放位置，不是四个要业务分别设置的开关。HTTP/2 Server Push 及 Push Cache 已在 Chrome 中移除，不要再把它排进缓存优先级。

常见坑

  • no-cache 当成「每次都不缓存」。真正不落地是 no-store。
  • Set-Cookie 是响应头，由服务器写入。页面脚本用 document.cookie。前端不能靠自己发一个 Set-Cookie 头给自己。
  • Cookie 约 4KB 且会进请求，不适合当资源缓存。localStorage 只存字符串，大约数 MB，对象要 JSON.stringify，没有 JSON.strJSON 这个方法。
  • sessionStorage 在刷新后还在，关掉该标签才没。它不是所有标签共享的会话。
  • IndexedDB 有源配额，不是无限空间，也不是同步 API。Web SQL 已废弃并被移除。
  • 只给接口加 max-age 而不改 URL，用户会在新鲜期内一直看到旧的 JS。要更新入口 HTML，或给文件名加哈希。

怎么配静态资源

一次发布可以分成两类 URL：

  • index.html：Cache-Control: no-cache，浏览器每次都向服务器验证。内容没变就 304，变了就拿到指向新哈希文件的 HTML。
  • app.[hash].js、带指纹的图片：Cache-Control: public, max-age=31536000, immutable。文件名变了才是新资源，旧文件可以留在缓存里直到自然淘汰。

协商缓存依赖验证器。有 ETag 就不要只靠 Last-Modified：一秒钟内两次写入，时间戳可能不变。弱 ETag（W/ 开头）允许语义等价，强 ETag 要求字节一致。

Vary 会把缓存按请求头拆开。接口若根据 Accept-Encoding 或 Origin 返回不同正文，漏写 Vary 会把别人的响应发给当前用户。带 Authorization 的响应通常应 private，避免共享缓存把私人数据发出去。

开发时勾上「Disable cache」只影响打开开发者工具的这次会话，不能代替正确的响应头。

验证一次请求

打开开发者工具的网络面板，看这几列就够判断策略对不对：

  1. 首次访问带哈希的脚本，状态是 200，响应头有 Cache-Control: max-age=31536000。
  2. 刷新后同一 URL 显示 (disk cache) 或 (memory cache)，没有新的请求头发出去。
  3. 刷新 index.html，请求仍然发出，资源未变时状态是 304，请求头里带 If-None-Match。
  4. 改过文件并重新构建后，HTML 指向新的文件名，旧脚本不再被引用。

若第 2 步仍每次都是 200 且有完整下载，说明强缓存没生效：要么 no-store，要么 URL 上加了随机查询参数。给静态文件加 ?t= 时间戳会让缓存键永远是新的，和长期缓存互相抵消。接口动态数据才需要协商或 no-cache。

HTML 入口不要长期强缓存，否则用户会一直用旧的文件名去要已经删除的脚本。哈希资源才使用一年的 max-age：

HTML 使用 Cache-Control: no-cache，让浏览器每次用 ETag 问服务器。no-cache 仍会把响应存下来；完全不存用 no-store。给脚本 URL 加随机时间戳等于放弃强缓存，只适合调试。

内存缓存和磁盘缓存是浏览器存放 HTTP 响应的位置，页面不能分别指定。Service Worker 若调用了 respondWith，可以在这之前给出自己的 Cache Storage 结果。HTTP/2 服务器推送已经从 Chrome 移除，不要再把 Push Cache 写成第四级必经缓存。

往返缓存（bfcache）保存的是整页快照，用户点后退时可能不重新发请求。它和 Cache-Control 不是同一套开关，unload 监听反而会让页面进不了往返缓存。

协商失败时看验证器是否真的发出去了：

  • 有 ETag 时，下一次请求应带 If-None-Match。
  • 只有 Last-Modified 时，下一次请求应带 If-Modified-Since。
  • 两个都没有，浏览器只能重新下载，不会出现 304。

小结

新鲜则强缓存，不新鲜再协商。no-cache 仍会存储，no-store 才禁用。哈希文件名配长 max-age，HTML 用 no-cache。Push Cache 和 Web SQL 都已过时，Cookie 也不是前端用 Set-Cookie 写出来的缓存。
