JS Event Loop

2019-07-15
  • JS
本文总阅读量次

他会再无忧虑也再无恐惧，四季转换，岁月静好。许多年后他们要是有机会还能相逢一笑，这可能是他们最好的结果。

概念

JavaScript 执行同步代码时只有一条调用栈。定时器、网络、DOM 事件由宿主环境在合适的时机把回调送进任务队列，Event Loop 负责在栈空下来之后取出任务执行。

浏览器里一轮的顺序是：

  1. 取一个宏任务（task）执行到结束。整段脚本本身就是第一个宏任务，其中的 console.log 是同步调用，不会再进一次任务队列。
  2. 清空微任务队列，包括这段期间新排进去的微任务，直到队列空。
  3. 可能进行渲染（requestAnimationFrame 在渲染前，不属于微任务）。
  4. 再取下一个宏任务。

不是「一进异步队列就先看微任务」。没有执行完当前宏任务之前，不会插进微任务阶段；当前宏任务（含整段脚本）结束后，才会把微任务全部跑完，然后才是下一个宏任务。

常见分类：

宏任务 微任务
setTimeout / setInterval Promise.then / catch / finally
I/O、UI 事件、postMessage queueMicrotask、MutationObserver
setImmediate（Node） await 后面的继续执行

new Promise(executor) 的执行器是同步的。只有 .then 注册的回调才是微任务。async 函数在第一个 await 之前也是同步的。

Node 里 process.nextTick 比 Promise 微任务更早，不要和浏览器模型混用。

正确示例

顺序：同步输出 start、end，并排好定时器与第一串 then。脚本这个宏任务结束后清空微任务：promise1 再排入 promise2。然后才执行定时器：打印 setTimeout，排入嵌套定时器，排入 promise3，同步执行内层执行器打印 1111。定时器回调结束，再清空微任务 promise3、promise4。最后那个嵌套 setTimeout 才打印 2222。

常见坑

  • 把整个 Promise 当成宏任务。执行器里的 console.log 若写在当前脚本顶层，会在 end 之前打印。
  • .then 链不是一次排完。后一个 then 要等前一个回调执行时才入队，所以 promise1 和 promise2 之间可以插入别的微任务。
  • setTimeout(fn, 0) 不是「立刻」，至少要等当前宏任务和其后的微任务，还受浏览器最小延时（嵌套定时器可达 4ms）影响。
  • async 函数返回的是 Promise。await 一个普通值，也会把后续代码排成微任务，所以 await 后面的代码晚于当前同步段。
  • 微任务里再排微任务会在渲染前全部跑完，长链会卡住绘制。把大块工作拆进宏任务或 requestIdleCallback。

微任务里再排队

then 回调执行时又注册的 then，会排进当前这一轮微任务的末尾，而不是等下一个宏任务。所以下面的 inner 会排在 promise2 前面还是后面，取决于它在哪个回调里注册：

同步代码结束后，微任务顺序是 a、c、inner、b。b 要等前一个 then 执行时才入队，因此晚于 a 里面新加的 inner，也晚于脚本末尾已经排好的 c。

async 函数遇到 await 就相当于把后半段放进微任务。await 一个非 Promise 值，也会晚于当前调用栈里剩下的同步代码。不要用长长的微任务链做动画，绘制要等这一轮微任务清空。requestAnimationFrame 在下一次绘制前运行，既不是 then 也不是 setTimeout。

Node 的 process.nextTick 比 Promise 微任务更早，把浏览器里的题搬到 Node 直接对输出，会差一截。

小结

一个宏任务，然后清空所有微任务，然后才是下一个宏任务或渲染。Promise 执行器同步，then / await 才是微任务，setTimeout 是宏任务。
