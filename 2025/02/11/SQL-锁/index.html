SQL 锁

2025-02-11
  • SQL
本文总阅读量次

不问缘由知底里，何如静默待流莺。

锁解决什么

  • 多个事务同时改同一份数据时，锁让后来的写入等待或失败，避免互相覆盖。读要不要等，取决于锁的种类和隔离级别。
  • 下面以 MySQL 为例。InnoDB 的行锁加在索引记录上，条件用不上索引时，可能锁住更多记录，甚至退化为锁整张表的效果。

按粒度

  1. 表锁
  • 锁整张表。MyISAM 以表锁为主。开销小、加锁快，没有行级死锁，并发也低：一个写锁会挡住别人的读和写。
  • 语法是 LOCK TABLES / UNLOCK TABLES（都是复数）。READ 时，本会话可读、其他会话也可读，任何人不能写。WRITE 时，只有持锁会话能读写，其他会话的读和写都等待。
  • LOCK TABLES 会隐式提交当前事务。InnoDB 业务代码里更常用行锁，而不是把整表锁上。
  1. 行锁
  • InnoDB 对索引记录加锁。开销比表锁大，锁的范围小，并发更高，也会出现死锁。死锁被检测到后，引擎回滚其中一个事务。
  • 自动提交打开时，这条 SELECT 结束锁就释放了。要在随后的 UPDATE 之前一直持有，把它们放进同一个事务。
  • 列名是 user_id。写成 user id（中间空格）是语法错误。
  1. 间隙锁与临键锁
  • 在 REPEATABLE READ 下，InnoDB 还会锁住索引记录之间的间隙，避免其他事务往这个范围里插入，用来挡住幻读。记录锁加上前面的间隙，称为临键锁（next-key lock）。
  • 等值命中唯一索引时，往往只留下记录锁，间隙可以放开。范围条件、非唯一索引更容易把间隙也锁上。

共享锁与排他锁

  • 共享锁（S）允许其他事务再拿共享锁来读，不允许排他锁。加锁读的写法是 FOR SHARE（MySQL 8.0+）或旧写法 LOCK IN SHARE MODE。
  • 排他锁（X）用 FOR UPDATE 或真正的 UPDATE / DELETE。其他事务对同一记录的加锁读、写都要等待。
  • InnoDB 普通的 SELECT 是一致性读，走快照，不加行锁，也不会被别人的行锁挡住。所以「排他锁让任何人都不能查询」只适用于 LOCK TABLES ... WRITE 这种表锁，不适用于 InnoDB 的 FOR UPDATE。
  • InnoDB 还有意向锁（IS / IX），标在表上，表示事务打算在某些行上加 S 或 X。它用来让表锁和行锁能够共存判断，不用逐行检查。

乐观锁与悲观锁

  • 悲观锁假定冲突会经常发生，用引擎的锁把行占住，例如事务里 SELECT ... FOR UPDATE 再更新。冲突多、事务短时合适。
  • 乐观锁假定冲突少见，不加数据库锁。给行一个 version，更新时带上读到的版本：
  • 受影响行数为 0，说明版本已经变了，应用读出新行再决定是否重试。这个检查是应用程序和 WHERE 一起完成的，引擎不会自动做。

常见坑

  • 只锁了 WHERE 用到的索引。根据另一条索引去更新同一行的事务，仍可能和这次锁冲突，因为最终都会锁到记录。
  • 事务里按不同顺序更新两行，两个会话容易死锁。约定按主键顺序更新，或捕获死锁错误后重试。
  • LOCK TABLES 期间，本会话只能访问已经点名的那些表，联表查询漏锁一张表就会报错。用完立刻 UNLOCK TABLES。
  • 长事务持有 FOR UPDATE，后面的写入会排起队。先把外部调用做完，再开事务锁行、更新、提交。

死锁时长什么样

  • InnoDB 选择回滚代价较小的那个事务，另一个继续。应用捕获 40001 / 1213 后，把整笔事务重试，而不是只重试最后一条语句——前面的语句已经随着回滚撤销了。
  • SHOW ENGINE INNODB STATUS 里的 LATEST DETECTED DEADLOCK 能看到两个事务各自持有哪把锁、在等哪把锁。按主键顺序更新，通常比加长锁等待超时更有效。
  • SKIP LOCKED（MySQL 8）跳过已被其它事务锁住的行，适合队列：多个工人各取一条还没人处理的评论。它会少读行，不能用在「必须处理到每一个匹配行」的对账上。NOWAIT 则是遇到锁立刻报错，由应用决定是否重试。
