微服务 Sentinel 服务保护

2025-11-21
  • 微服务
本文总阅读量次

宜未雨而绸缪，毋临渴而掘井。

对应练习

  • 控制台：Sentinel Dashboard，默认端口 8858
  • 入口：hm-gateway 上按路由限流
  • 服务内：商品查询、下单等接口上的 @SentinelResource
  • 远程调用：配合 OpenFeign 的 fallbackFactory（见 OpenFeign 篇）

为何需要流控、降级、熔断

调用链一长，下游一慢，上游线程就堆住：

手段 做什么
流控 进来的量超过阈值就拒绝或排队，保住本服务
熔断 下游错误或慢调用过多时暂停调用，快速失败
降级 被限流或调用失败后，给出可接受的托底结果

三件事叠在一起，是为了把故障留在局部：详情页可以返回「稍后再试」，下单失败必须让用户看见，不能假装成功。

控制台在看什么

Sentinel 把要保护的代码叫做资源。应用把资源的通过量、拒绝量报到控制台，规则在应用进程里执行。

  • 左侧列表是 spring.application.name。eager: true 让进程启动就连上，不必等第一次访问。
  • 控制台能配流控、熔断、热点参数、系统规则（CPU、负载）。
  • 规则默认在内存里，重启就没了。练习可以现配；要保留就接到 Nacos。

接入

@SentinelResource

保护本服务自己的接口时，直接标在方法上：

回调 何时进入
blockHandler 流控、熔断、系统保护触发，末尾参数是 BlockException
fallback 业务方法自己抛出异常
  • 回调与原方法同属一个类（或用 blockHandlerClass），参数列表要兼容。
  • 资源名必须和控制台规则一致。
  • 热点规则按参数限流，例如同一个商品 id 被刷时单独收紧。

网关流控思路

流量先在 Gateway 挡住，比每个服务各自为战省连接。引入 Sentinel 的网关适配后，规则有两种资源维度：

  1. 路由 ID：整条 lb://item-service 共享一个配额。
  2. API 分组：把 /items/** 收成一个名字，再对这个名字限流。

阈值一般用 QPS。也可以按 Header（例如用户标识）做热点，避免一个账号占满入口。超过阈值直接在网关返回，例如状态码 429，请求到不了订单服务。

入口配额按下游真实容量来留余量：网关放得太宽，请求进了服务仍被拒绝，下游连接已经被占住。Gateway 篇里的 RequestRateLimiter 是另一条入口限流实现，和 Sentinel 二选一做主方案，避免两套阈值互相打架。

与 Feign 降级配合

  • 本服务入口用 @SentinelResource。
  • 调别人时打开 feign.sentinel.enabled，在 @FeignClient 上挂 fallbackFactory。远程超时、连接失败，以及 Sentinel 阻断，都进工厂。

查询可以返回空列表或缓存副本。扣库存、创建订单的托底要抛出业务异常，让订单失败可见，再由用户重试或走补偿。

常见规则

规则 看什么 适合
QPS 流控 每秒通过次数 商品详情这类读接口
线程数流控 尚未返回的并发调用 下游变慢、线程被占满
慢调用比例 超过最大 RT 的占比 依赖偶发变慢
异常比例 / 异常数 错误占比或绝对次数 依赖持续报错

慢调用比例要同时看统计窗口、最小请求数、比例阈值和熔断时长。请求太少时不熔断，避免两三笔慢请求就打开开关。熔断时长结束后放少量探测，探测仍慢就继续打开。QPS 看每秒放行次数，线程数看尚未返回的并发；下游变慢时线程会先满。排队要带等待上限，排不上就拒绝。

排错

现象 排查
控制台没有应用 地址端口、eager、网络
规则不生效 资源名、是否配在对应应用下
重启规则丢失 仍在内存，需持久化
熔断后一直失败 熔断时长未到，或探测请求仍失败
降级没执行 回调签名不对，或异常被别的切面先接走

小结

  • 流控保住自己，熔断截断故障，降级决定用户看见什么。
  • 先对一个查询接口配 QPS，在控制台看拒绝数，再给 Feign 调用配慢调用比例。
  • 写操作的托底只能是明确失败。超时配置仍然要留着，Sentinel 替代不了客户端超时。
