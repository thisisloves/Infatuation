中间件 消息队列选型

2025-07-22
  • 中间件
本文总阅读量次

不积跬步，无以至千里。

先对齐四个维度

消息队列用来解耦、削峰、把一笔业务的后续动作挪到请求之外。RabbitMQ、Kafka、RocketMQ 都能做这三件事，差别在吞吐、顺序、事务消息和运维成本。选型先对这四列，再对业务，避免用一种队列包下所有场景。

常规投递都可能重复，也可能延迟。消费端用业务键做幂等。这条和选哪一种队列无关。

维度 RabbitMQ Kafka RocketMQ
吞吐 中等，适合任务和业务事件 最高，面向日志和流 高，面向交易类消息
时序 单队列、单消费者时接近入队顺序 分区内有序，按键可固定分区 顺序消息在同一个队列内有序
事务消息 发布确认，本地库一致自己拼 事务范围在集群内部 半消息、提交或回滚、回查
运维 模型要先懂，管理台直接 分区、副本和磁盘要提前规划 NameServer + Broker，Java 栈好接手

RabbitMQ

模型是交换机把消息路由到队列。Direct、Topic、Fanout 能表达「这条消息给谁」，路由规则比另外两种细。管理台可以看见队列、连接和堆积。单机吞吐低于 Kafka，换来的是这种路由。

顺序只在「一个队列、一个消费者」时接近入队顺序。多个消费者一起抢，谁先处理完谁先往下走，完成顺序就散了。要严格按序，就得收成单消费者，吞吐跟着下来。

可靠发送用发布确认：Broker 接住消息后再回调。和本地数据库一起成功，需要自己做本地消息表或发件箱，先记库再投递、失败再扫表。它适合中等流量、路由复杂、要延迟后处理的任务，例如通知、积分、超时关单。

Kafka

消息按主题分成多个分区，顺序写盘，消费者按组拉取。吞吐放在第一位，适合行为日志、指标、风控事件流。分区数决定并行度，也决定文件和副本怎么铺，这是运维里最重的一块。

同一个分区里，读取顺序和写入顺序一致。把订单号这类键哈希到固定分区，就得到按键有序。不同分区之间没有统一顺序。全局排序会把并行度打回一个分区。

Kafka 事务把发往多个分区的消息，以及消费位点，做成一次原子提交，配合幂等生产者，解决的是集群内部的重复和半套写入。它不回查业务库里的事务结果。数据库和 Kafka 要同时成功，仍然用发件箱。元数据由 KRaft 管理；还停在较老版本的集群，则要另外运维一套 ZooKeeper。

RocketMQ

主题下面再分队列，Broker 存消息，NameServer 告诉客户端 Broker 在哪，自己不存消息。吞吐对订单、支付这一类业务通常够用，模型比 Kafka 的海量日志更靠近「一笔业务一条消息」。

普通消息不保证全局顺序。顺序消息按业务键选一个队列，这个队列内按序消费，并行度等于这类键分散到的队列数。延迟投递、死信、按 Tag 过滤，都是直接面向业务的能力。

事务消息是它和另外两种最明显的差别：

本地事务成功，消息最终会出现在队列里；本地事务失败，半消息被丢掉。回查用来补上「提交结果在路上丢了」的窗口。消费端仍可能收到不止一次，幂等键还是要有。Java 进程加控制台就能看堆积，运维重于单机 RabbitMQ，轻于要规划大量分区和磁盘保留时间的 Kafka。

顺序、事务和堆积

三个要求会互相挤占，要一起定。

顺序若要并行，就把键散列到多条流：Kafka 用分区，RocketMQ 用队列，RabbitMQ 用多个队列配合一致哈希。相同键留在同一条流里才有顺序。全局顺序要求只留一条流，并行度跟着下降。

事务消息要解决库和消息同成同败。

队列 和本地库怎么对齐
RocketMQ 半消息写进协议，Broker 会回查
RabbitMQ 发布确认保证进了队列，库侧用本地消息表
Kafka 事务覆盖多个分区和消费位点，库侧仍用发件箱

消费端都要准备收到重复消息。堆积的位置也不同：Kafka 与 RocketMQ 把消息放在磁盘日志里，消费者慢慢拉。RabbitMQ 更积极地推给消费者，堆得太大时内存上涨，需要惰性队列，或限制每次预取的条数。尖峰会留很久，优先磁盘日志；消息要按规则马上转发、量又不大，用 RabbitMQ。

运维上先问三件事

  • 谁值守。熟悉交换机和管理台、流量中等，用 RabbitMQ。团队以 Java 为主、要事务消息，接手 RocketMQ 的 NameServer 和 Broker。下游是流处理，再承担 Kafka 的分区和磁盘。
  • 留多久。Kafka 按时间或大小保留，消费者可以回头重放。RabbitMQ 在消息确认后从队列删除，不负责长期留存。RocketMQ 也有保留期限，过期会清掉，不拿它当审计账本。
  • 延迟多细。RabbitMQ 用过期加死信做出延迟。RocketMQ 直接延迟投递。Kafka 按分区尽快送达，到点处理通常写在消费者里。

副本用来防机器或磁盘损坏，不改变种类选择。副本越多，写要等更多份确认，吞吐越低。钱和库存的一致性优先于吞吐。

什么业务选哪个

  • RabbitMQ：路由规则多，量级有限，要管理台和延迟任务。短信、积分、按规则扇出，放这里。
  • Kafka：写入量极大，要按键有序，下游是流处理或日志检索。用户行为、监控指标，放这里。
  • RocketMQ：本地事务和消息必须同成同败，或同一业务键要按序消费。下单、支付结果、扣减通知，放这里。

一套系统里可以并存：日志进 Kafka，订单进 RocketMQ，通知进 RabbitMQ。按场景拆，比全局押一种队列更不容易在顺序或事务上补锅。量很小、调用方只需要马上知道结果时，直接调用即可，不必先引入队列。

和本站 RabbitMQ 篇

本篇只做选型。交换机、绑定、发布确认和几种消费方式，见《RabbitMQ》。堆积时的内存、延迟关单和可靠投递，见《微服务 RabbitMQ 高级》。那两篇沿 RabbitMQ 往下讲，不比较 Kafka 和 RocketMQ。选定 RabbitMQ 之后，路由和确认按那两篇落地；选定另外两种，就不要把交换机模型照搬过去。

小结

  • 吞吐 Kafka 最高，RocketMQ 覆盖多数交易消息，RabbitMQ 强在路由。
  • 顺序都是「一条流里面有序」：RabbitMQ 看单消费者，Kafka 看分区，RocketMQ 看顺序队列。
  • 要和本地事务绑在一起，用 RocketMQ 的半消息和回查；Kafka 事务只管集群内部。
  • 选型看本篇。RabbitMQ 的交换机和可靠投递，看本站对应的两篇。
