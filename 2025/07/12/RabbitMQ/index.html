RabbitMQ

2025-07-12
  • RabbitMQ
本文总阅读量次

我寄愁心与明月，随君直到夜郎西。

对应练习

  • 工程：mq-demo
  • publisher：发送、Confirm / Return
  • consumer：SpringRabbitListener + 多种 Exchange 配置类

为什么需要 MQ

场景 作用
下单后发短信 / 积分 异步解耦，缩短接口耗时
秒杀流量 削峰，保护下游
多服务最终一致 用消息驱动补偿

核心概念

概念 含义
Exchange 交换机，决定消息怎么路由
Queue 队列，存消息
Binding 交换机与队列的绑定关系
RoutingKey 路由键

发布端配置

可靠性

  1. Confirm：Broker 是否收到（到 Exchange）。
  2. Return：Exchange 有了但没法进任何 Queue（路由失败）。
  3. 业务上常配合 本地消息表 / Outbox，避免「业务成功但消息没发出」。

消费端：工作队列

  • 多个消费者监听同一队列 → 竞争消费（能者多劳）。
  • 注意消费者处理速度差异带来的负载不均。

Fanout / Direct / Topic

类型 行为
Fanout 忽略 routingKey，广播到所有绑定队列
Direct routingKey 完全相等 才投递
Topic 支持 * / # 通配

注解声明绑定

  • 启动时自动声明 Exchange / Queue / Binding，适合 Demo；生产常由运维或配置中心统一治理。

延迟队列（练习中有 DelayExchangeConfig）

  • 常见用途：订单超时关单、延迟重试。
  • 实现：延迟插件，或 TTL + 死信交换机 模拟。

ACK 与重试

  • 失败消息可进死信队列（DLX），避免无限毒丸消息。
  • 消费逻辑务必 幂等（同一消息多次送达只生效一次）。

与微服务订单链路的关系

  • 强一致扣款库存仍可能用 Seata；能异步的尽量异步，降低分布式事务范围。

小结

  • 先把 Work / Fanout / Direct / Topic 四种模型用 mq-demo 跑通。
  • 再打开 Confirm / Return / 延迟队列，理解「可靠投递」与「延迟业务」。
  • 业务里按主题命名消息，把 Demo 迁到实际交换机与队列。
