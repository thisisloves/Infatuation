对应练习

  • 端口：9200（HTTP）
  • 索引：商品 items，一条文档对应一个商品 id
  • 数据来源：item-service 的商品表
  • 分词：IK，版本与 ES 版本对齐，否则节点起不来

商城列表上的「关键字 + 品牌 + 价格区间 + 销量排序」不适合每次数 LIKE。ES 负责搜索，MySQL 仍是商品主数据。

倒排索引

正排是「文档里有哪些词」。倒排是「词出现在哪些文档」：

搜索「机械键盘」时，取出两组文档求交，再按相关度排序。倒排里还可以带词的位置，用来做短语匹配。商品名称走这条索引；价格、品牌这类过滤字段按原值存储，不参与切词。

索引、文档、映射

概念 对应关系
索引 index 一类文档的集合，这里是 items
文档 document 一个商品，_id 用商品 id
映射 mapping 字段类型和分词器，相当于表结构
  • text 会分词，用于名称。
  • keyword 不分词，用于品牌、类目、上下架状态。
  • price 用长整型，单位是分，避开浮点。
  • 生产环境把动态映射收紧，避免一次脏写入把价格建成字符串。

文档 id 固定为商品 id，后写的内容覆盖先前的文档，重复同步也不会出两行。

IK 分词

标准分词器按字切开中文，召回和相关度都差。IK 按词典切词：

分词器 粒度 用在哪
ik_max_word 最细 写入索引，提高召回
ik_smart 较粗 搜索语句，减少噪声

品牌、型号可以补进扩展词典，否则「Cherry」可能被切碎，筛选对不上。改词典后要重建索引，旧数据不会自动重切。

基础查询

match 会把查询句分词再匹配，用在 name。term 按原值匹配，用在 keyword。把 term 用在已经分词的 name 上，常常一条都命不中，因为索引里没有整句原文。

bool 把条件拼起来：must 参与评分，filter 只过滤、不评分，价格和品牌放这里，结果还可以被缓存。

价格条件是 100 元到 500 元（按分存储）。排序按销量。浅分页用 from / size 即可，商城很少翻到很深。

下架商品在过滤里要求 status = 1，或者同步时直接删掉文档。两种都要统一，避免搜到不能卖的商品。

与 MySQL 同步

搜索允许秒级延迟。主数据以 MySQL 为准，ES 是派生索引。

方式 做法 适合
双写 更新数据库后再写 ES 改动面小；失败时要有补偿扫描
MQ 事务提交后发商品 id，搜索服务覆盖文档 已有 RabbitMQ 时优先
Canal 订阅 binlog，解析商品表再写 ES 业务代码不用改；多一套组件

MQ 的消费端按商品 id 覆盖或删除，天然幂等：

双写时，数据库成功而 ES 失败会造成「库里有、搜不到」。补偿任务按更新时间把最近变更再推一次。Canal 从 binlog 读，对业务无感，表过滤和位点要单独守。

商品变更的路由可以是 item.update，和订单消息分开，避免搜索消费堵住关单。

小结

  • 名称用 IK 的 text，品牌和状态用 keyword，价格用分。
  • 查询用 match + bool.filter，文档 id 用商品 id。
  • 同步优先走已有的 MQ；双写和 Canal 按「能不能改业务、能不能多一个组件」选择。
