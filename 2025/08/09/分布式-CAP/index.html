分布式 CAP

2025-08-09
  • 分布式
本文总阅读量次

读书破万卷，下笔如有神。

C、A、P 各指什么

CAP 说的是多副本、会跨网络的系统，在分区出现时能承诺什么。三个字母各有固定含义。

一致性 C：一次写入完成后，之后任何一次读都要看到这次写入，否则就明确失败。副本之间不能一个新、一个旧还都当成功。这里的 C 是线性一致：读到的是最新已提交写入。

可用性 A：每个没有崩溃的节点，都要在有限时间内给出响应。响应可以不是最新的，但不能一直不答，也不能一律回答「现在不可用」。

分区容错 P：节点之间的消息可以丢失、延迟，或者网络被切成互不可达的两半。系统在这种前提下仍按自己的设计继续运行。

ACID 里的 C 要求一笔事务前后满足约束，例如余额不为负。CAP 里的 C 要求各副本的读结果是最新写入。两个 C 讨论的不是同一件事。

分区时为什么只能保一边

机器用网络连起来，丢包和延迟就会发生。跨机系统把 P 当作前提：设计里要写明分区出现后怎么办。把 P 当成可选项，等于假设链路永远正常。

分区把集群切成 N1、N2，两边暂时传不了消息。N1 已经完成一次写入。

N2 若必须回答，它手里没有新写入，只能返回旧值，C 保不住，这是 AP。N2 若必须避免返回旧值，就得拒绝这次请求，A 保不住，这是 CP。消息过不去的那一刻，做不到既返回最新值，又保证每个未崩溃节点都给出成功响应。

没有分区时，N2 收得到写入，既可以返回最新值，也可以正常响应。C 和 A 在这段时间里同时成立。定理约束的是分区已经发生的时刻，要在 CP 和 AP 两条路线里选一条。三个性质不会在分区当下同时拉满。常见的「三选二」把 P 画成和 C、A 并列的可选项，跨机部署里选的其实是：分区一来，保 C 还是保 A。

单机数据库没有节点之间的网络，进程内可以同时给出最新读和正常响应。那是没有分区要容忍的场景，套不到多副本的取舍上。

一次请求怎么选边

写成功的标准随路线改变。

  • CP：多数派确认后才返回成功，此后多数派上的读能看到它。打到失联少数派，得到失败或超时。
  • AP：单个副本可以先返回成功，其它副本稍后追上。读到还没追上的副本，结果是旧值。
数据 路线 分区时客户端看到什么
选主、锁、配置 CP 少数派失败，避免两个主或两把锁
服务注册表 AP 仍返回列表，里面可能有过期地址
可重建的缓存 AP 仍返回内容，允许短暂旧值
库存余额 单主事务 副本可以旧，扣减只认主库已提交的结果

消息只是变慢、最终还能到，这还不是分区。分区指在约定时间内无法确认对方。超时越短，越容易把慢当成已经切开。

CP 的读可以再分一层。线性读会和多数派确认本节点仍有最新日志，从而得到已提交写入。跟随节点直接回答更快，可能略旧，但写仍要多数派，不会留下两套已提交数据。etcd 的线性读做这次确认；ZooKeeper 可以先和领导对齐再读。AP 的注册中心默认读本地这份表，新鲜度靠心跳和复制补上。

客户端看到的失败也不一样。CP 的错误是此刻没有多数派，重试要落到多数派一侧。AP 返回的是可能旧的成功响应，再试一次拿到的仍是这份副本上的结果。无分区时，副本彼此通着，CP 同样可以又快又新。分区愈合、落后副本追上之后，两条路线都会回到同一份数据。

常见系统落在哪

分类看的是分区发生时，系统选择继续应答，还是停下来守住一致。下表是倾向，不是说另一项在无分区时完全缺失。

系统 倾向 分区时的行为
ZooKeeper CP 写入要多数派确认。落在少数派的节点不接受写，避免两边各提交一份
etcd CP 用 Raft。选举和写入都要法定人数，少数派在分区期间不接写
Eureka AP 各节点继续提供注册表，允许读到过期实例；自我保护避免抖动时大批摘除
Nacos 可切换 临时实例走 Distro，偏向 AP；持久实例和配置走 Raft，偏向 CP

ZooKeeper 的读若直接打到尚未同步的节点，可能看到稍旧的状态。写路径要求多数派，工程上仍把它放在 CP 一侧：少数派宁可不可写，也不分成两套已提交数据。

etcd 同样把法定人数放在写和选主上。少数派分区期间不接受写，客户端会等到多数派或收到失败。

Eureka 在分区两侧都继续登记和查询。自我保护是：心跳大面积丢失时停止淘汰实例，注册表宁可旧着，也保持可查询。调用方要能接受实例列表暂时过期。

Nacos 的切换点在实例类型。临时实例靠心跳维持，节点间异步复制，注册发现偏向 AP。持久实例不会因为心跳停止而消失，写入走 Raft，偏向 CP。配置数据也走 Raft，读到的是已提交的配置。注册时选临时还是持久，就是在这两种模型里选。

和 BASE、最终一致性

BASE 是选了可用性之后的工程说法，三件事：

  • 基本可用：分区时仍然响应，允许降级。例如先返回上一次的库存数字，并标明可能滞后。
  • 软状态：副本允许处于中间状态，一段时间内数字不同。
  • 最终一致：新的写入停下来之后，副本会收敛到同一结果。

最终一致性是 BASE 的第三条，也是 AP 系统常见的数据承诺。它承认读到的可以暂时落后，并要求这个窗口会结束。对账、补偿、读时修复，都是把窗口收口的办法。

CAP 回答的是分区当下保 C 还是保 A。BASE 回答的是选了 A 之后，业务如何对待暂时的分歧。CP 系统在分区时让少数派停止写入，多数派上保持已提交的一致。AP 系统继续应答，再用 BASE 把副本收成最终一致。

库存这类数字若走 AP，短时间里两个节点的剩余量可以不同，之后用对账或补偿对齐。协调、选主、配置这种不能分成两套的数据，用 ZooKeeper、etcd 或 Nacos 的 CP 路径，分区时让少数派失败，而不是返回一份各写各的结果。

小结

  • C 是读到最新写入，A 是未崩溃节点都要及时响应，P 是网络可以被切开。
  • 跨机系统把 P 当作前提。分区出现时保 CP 或 AP；没有分区时，C 和 A 可以同时提供。
  • ZooKeeper 和 etcd 偏向 CP，Eureka 偏向 AP，Nacos 用临时实例和持久实例在两边切换。
  • 选 AP 之后用 BASE 接受软状态，并做到最终一致。CAP 的三个字母不会在分区当下同时拉满。
