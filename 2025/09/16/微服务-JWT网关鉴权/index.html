微服务 JWT 网关鉴权

2025-09-16
  • 微服务
本文总阅读量次

一片冰心在玉壶。

对应练习

  • 模块：hm-gateway
  • 签发：user-service 登录成功后用 JwtTool 生成令牌
  • 校验：AuthGlobalFilter 解析令牌，把用户 id 写入请求头 user-info
  • 传递：下游 MVC 拦截器读取；OpenFeign 再把这个头带到下一次调用

为什么放在网关

拆开之后每个服务都能碰到「当前是谁」。如果 user、cart、order 各自解析 JWT，白名单和密钥要复制多份，漏改一处就会出现这家过了、那家 401。

浏览器只访问 hm-gateway。网关做三件事：白名单放行、校验 JWT、把用户 id 写入 user-info。业务服务不再接触密钥。OpenFeign 发往下游的新请求还要再带上这个头。

网关基于 WebFlux，鉴权用 GlobalFilter。在网关里注册 HandlerInterceptor 不会执行。拦截器写在后面的 Servlet 服务里。

这不能代替网络隔离。谁都能直接打到 cart-service 的端口时，伪造一个 user-info 就冒充了用户。练习环境业务端口留在内网，只把网关暴露出去。

登录时签发

user-service 校验账号密码，通过后用用户 id 做主体生成 JWT。令牌由三部分组成：头、载荷、签名。网关只验签并取出用户 id，不查数据库。

签发和校验必须用同一把密钥、同一种算法。任何一边改了密钥，现象都是登录看起来成功，随后所有业务接口 401。

前端之后每次请求把令牌放在 Authorization。本练习里头的值就是令牌本身。若约定成 Bearer 前缀，网关解析前要先去掉，两边保持同一种约定。

GlobalFilter

过滤器做四步：白名单直接过；读取 Authorization；解析失败返回 401；成功则先删掉外部传来的 user-info，再写入解析结果。不删除的话，调用方可以自己带头，在令牌对应的用户之外再塞一个 id。

getOrder 的值越小越靠前。鉴权要早于真正转发。返回的是 Mono，里面不要做阻塞查询。

下游读取用户

cart-service、order-service 用拦截器把请求头放进线程上下文，业务代码就不逐个方法去读请求了。请求结束必须清理，线程池会复用线程，残留的 id 会串到下一个人。

在 WebMvcConfigurer#addInterceptors 里注册。UserContext 用 ThreadLocal 保存用户 id，并在请求结束时 remove。@Async 或自建线程池不会带走这个上下文，要显式传用户 id。

排错

现象 排查
登录也 401 白名单是否包含登录路径，Ant 是否写窄了
登录成功，业务仍 401 密钥、过期时间、头名是否都是 Authorization
下游用户永远是空 网关是否写入 user-info；拦截器是否注册
Feign 过去后用户丢失 是否有 RequestInterceptor；调用是否换了线程
不带令牌也能指定用户 网关没有先删除外部传入的 user-info

小结

JWT 在 user-service 签发，在 hm-gateway 的 GlobalFilter 校验。白名单放行登录和公开查询，其余请求把用户 id 写进 user-info，并覆盖客户端自带的同名头。下游拦截器放进 ThreadLocal，OpenFeign 再显式传给下一个服务。
