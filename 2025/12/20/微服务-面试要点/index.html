微服务 面试要点

2025-12-20
  • 微服务
本文总阅读量次

大漠孤烟直，长河落日圆。

怎么用这篇

下面按问答短答整理，对应概述、Nacos、Gateway、OpenFeign、Sentinel、RabbitMQ、Seata、负载均衡各篇。CAP、Dubbo 另有专篇，这里只收微服务常问短答。

什么时候该拆服务？

短答：边界稳定、发布节奏不同、需要单独扩容时再拆。

人少、跨表事务很多且没有补偿时，先做模块化单体。详见《微服务 概述与拆分》。

按什么边界拆？

短答：按业务能力拆，一个服务拥有自己的数据。

按技术层拆成「只有 dao 的服务」会让每次需求改好几个仓库。hmall 按用户、商品、购物车、订单、支付拆。

数据库要一起拆吗？

短答：每个服务独占自己的库或 schema，别的服务通过接口访问。

练习阶段可以先逻辑分开。跨库查询改成调用，或冗余一份可延迟的数据。

CAP 怎么理解？

短答：网络分区时，在一致性和可用性之间取舍，分区容忍躲不掉。展开见《分布式 CAP》。

  • C：读到最新写入。
  • A：请求都有响应。
  • P：网络切开后系统还能运转。

注册中心可以短暂拿到旧实例列表（偏向可用）。支付记账宁可失败也不能记错（偏向一致）。

BASE 在业务上指什么？

短答：基本可用、允许中间状态、过一段时间达到一致。

订单主状态要明确。积分、搜索索引、短信可以稍后到。这就是商城里大量用消息的原因。

注册发现做哪几步？

短答：启动注册，调用方按服务名拉取实例，再负载均衡。

服务名、命名空间、Group 三处要和 Nacos 控制台一致。详见《微服务 Nacos 注册发现》和《微服务 负载均衡》。

网关鉴权为什么还要下游校验？

短答：网关负责拦外网；内网仍可能绕过网关，下游要认识用户身份。

白名单只放登录和验证码。用户 id 放进请求头往后传。详见 Gateway 与 JWT 两篇。

超时怎么定？

短答：连接超时短，读超时按下游耗时，上游等待要盖住下游。

商品读超时 1 秒时，订单侧的等待要更长，否则商品还在执行，订单已经放弃。

哪些调用可以重试？

短答：查询可以有限重试；创建订单、扣库存不要自动重试。

Spring Cloud OpenFeign 默认不重试。网关重试和客户端重试叠在一起会把超时放大，全链路只留一处。详见负载均衡篇。

幂等怎么做？

短答：同一请求执行多次，结果与执行一次相同。

创建订单用客户端带来的 requestId 做唯一键，冲突则返回已有订单号。扣库存用「库存不少于本次数量」的条件更新。消费消息用业务主键挡住重复投递。

分布式事务怎么选？

短答：先缩小事务范围，再按一致性强弱选型。

场景 选择
单服务单库 本地事务
下单同时扣库存，要求强一致 Seata AT，见 Seata 篇
可补偿的长流程 TCC 或 Saga
超时关单、加积分、改搜索索引 消息最终一致

消息最终一致怎么落地？

短答：本地事务写下业务和待发消息，提交后再投递，消费端按主键幂等。

  1. 订单入库与消息表同一事务。
  2. Confirm 成功后把消息标成已发送，失败由扫描补投。
  3. 消费者处理完再 ack；失败进死信。
  4. 15 分钟未支付的关单走延迟消息，见 RabbitMQ 高级篇。

熔断和降级各管什么？

短答：熔断是停止调用故障依赖；降级是给调用方一个托底结果。

流控则是本服务自己的入口配额。查询可以返回空列表；扣库存的托底必须是失败。详见 Sentinel 篇。

缓存和库谁为准？

短答：成交、库存以 MySQL 为准；Redis 是热点读和互斥；ES 是搜索派生索引。

改详情：先更新库，再删缓存，再发消息刷新索引。详见 Redis 篇与 Elasticsearch 篇。

Dubbo 和 Spring Cloud 怎么选？

短答：内网 Java 互调、要细粒度 RPC 治理时看 Dubbo；HTTP + 网关 + 多语言友好时看 Spring Cloud。

本站主线是 Nacos / Feign / Gateway。架构角色与对比见《微服务 Dubbo》。

速记

问题 一句
怎么拆 按业务，数据归服务所有
CAP 分区时在 C 和 A 之间取舍
发现 服务名 + 命名空间 + Group
鉴权 网关拦截，下游认用户头
重试 只重试幂等读，只留一处
事务 能异步就消息，强一致才 Seata
保护 流控、熔断、降级分开说
RPC Dubbo 偏 RPC；Cloud 偏 HTTP 生态

小结

面试先画调用链：网关 → 订单 → 商品 / 支付，再在链上指出注册、负载均衡、超时、幂等、消息和缓存各站在哪。答不上实现细节时，把取舍说清楚也算答到点上。
