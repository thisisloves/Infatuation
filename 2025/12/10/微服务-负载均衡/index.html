微服务 负载均衡

2025-12-10
  • 微服务
本文总阅读量次

潮平两岸阔，风正一帆悬。

对应练习

  • 注册：Nacos（8848），服务名如 item-service
  • 调用：OpenFeign、带负载均衡的 RestTemplate、Gateway 的 lb://
  • 组件：Spring Cloud LoadBalancer（Ribbon 已退出维护）

客户端负载均衡

实例有多台时，调用方自己从列表里选一台，再发 HTTP。选择发生在调用方进程里，所以叫客户端负载均衡。

浏览器只访问 Gateway。网关进程里对 lb://item-service 再选一台商品服务，这仍是客户端负载均衡，只是「客户端」是网关。

放在入口的 Nginx 是另一侧：它不读 Nacos，除非另外做集成。课程里的服务之间以注册中心的列表为准。

Spring Cloud LoadBalancer

Feign 和 lb:// 都走这套。引入 Nacos 发现后，列表的提供者是 Nacos，挑选器在 Spring Cloud Alibaba 里通常是 NacosLoadBalancer：它认识权重和集群。

只引入 LoadBalancer、没有 Nacos 那层自动配置时，默认挑选器是轮询 RoundRobinLoadBalancer。

@LoadBalanced 会在请求 http://item-service/... 时把服务名换成具体实例。Feign 的 name = "item-service" 走同一条路，不必再套一层自己写的选择逻辑。

常见策略

策略 行为 何时用
轮询 按顺序轮转 实例能力接近，且未启用 Nacos 权重
随机 均匀随机 调用很密、希望避开轮询的共享下标
权重 按 Nacos 的 weight 机器配置不同；摘流量时把权重调成 0
同集群优先 先选相同 cluster-name 多机房，减少跨机房调用

权重为 0 的实例可以仍在控制台里，但不会被分到流量，适合滚动发布前的摘除。改权重后等客户端刷新列表，再观察新请求落在哪一台。

与 Nacos 实例列表的关系

LoadBalancer 不负责注册，只消费一份实例列表：

列表里已经去掉了心跳超时的实例，也受命名空间、Group 过滤。调用方和提供方筛选项不一致时，列表是空的，表现往往是「服务不可用」，而不是「选错机器」。

列表健康只说明 Nacos 还收到心跳。进程活着但接口卡死时，它仍会留在列表里，所以还要有超时和 Sentinel。负载均衡解决「选谁」，不证明「选中的那台业务正常」。

超时和重试

超时分成两段：连不上用连接超时，连上了但响应慢用读超时。

Spring Cloud OpenFeign 默认 Retryer.NEVER_RETRY，不会在 Feign 里自动再打一次。上面把 LoadBalancer 重试也关掉，避免和网关重试叠乘。

若网关要对失败换一台，只覆盖查询：

数量级要心里有数：读超时 1 秒、连接超时 300 毫秒，重试 1 次，最坏大约两次读超时加上连接时间。网关再重试一轮，等待会再翻倍，故障实例也被打得更重。写操作不进这套重试，创建订单用唯一 requestId（见面试要点篇）。

查询商品详情可以换实例再试一次。扣库存、创建订单失败时返回错误，由用户或补偿任务处理，不在负载均衡层自动再来一遍。

排错

现象 排查
找不到实例 服务名、命名空间、Group、是否已注册
总打到旧机器 权重、列表刷新、下线实例是否还在心跳
偶发整页很慢 重试次数相乘、读超时过大
重复下单 写接口被重试，且没有唯一请求号
跨机房很慢 cluster-name 不一致，同集群优先没生效

小结

  • 选实例发生在 Feign、RestTemplate 和 Gateway 进程里，候选集来自 Nacos 的健康列表。
  • 有 Nacos 权重和集群时用 NacosLoadBalancer；权重 0 用来摘流量。
  • 超时分开配置；重试只留给幂等的 GET，并且全链路只留一处。
