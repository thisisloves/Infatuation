微服务 概述与拆分

2025-12-01
  • 微服务
本文总阅读量次

会当凌绝顶，一览众山小。

对应练习

  • 工程：hmall
  • 从单体里拆出 item-service、cart-service，调用方用 RestTemplate 访问
  • 相关服务还有 user-service、order-service、pay-service

单体、微服务、Spring Cloud

单体是一个进程、一次打包、一套库。hmall 最初登录、商品、购物车、订单、支付都在同一个工程里，本地方法互相调用，事务也好做。

它的麻烦在后面才出现：改购物车要整包发布；商品查询流量高，却只能把订单、支付一起扩容；一个模块把堆打满，整个站点不可用。

微服务按业务能力拆成独立进程，各自部署、各自扩容。代价是网络会失败、超时、重试，数据不再能靠一个本地事务兜住。这些代价要用注册中心、远程调用、网关和配置中心补上。

Spring Boot 负责单个服务怎么启动。Spring Cloud 是旁边的治理工具，不是另一种业务写法。hmall 用的 Spring Cloud Alibaba，注册和配置走 Nacos，服务之间的声明式调用走 OpenFeign，入口走网关。拆分练习的第一步先用 RestTemplate，把「本地方法」换成「远程 HTTP」。

单体 微服务
部署 一个包 按服务独立发布
扩容 整站复制 只扩热点服务
调用 进程内方法 网络，要处理超时和失败
数据 一个库，可以 join 每服务自己的库

hmall 的业务链路

一条购物链路穿过多个服务，后面所有远程调用都从这里长出来。

搜商品读多写少，适合单独扩容。下单同时碰库存和购物车，是跨服务写，不能再靠一个 @Transactional 包住两个库。

何时拆、怎么拆

出现这些情况再拆：发布节奏不同、某一块需要单独扩容、故障要隔离开、不同人长期改不同模块。没有这些压力时，拆开只是把方法调用换成网络调用。

拆分时守住四条：

  1. 按业务能力拆，不按 controller、service、mapper 这种技术层拆。不存在「只有 dao 的服务」。
  2. 高内聚。一起改、一起发布的功能留在同一个服务。
  3. 调用链要短。购物车可以查商品，商品服务不要再回调购物车。
  4. 数据库按服务分开，禁止跨库 join。需要别的服务的数据，就远程查询，或在本库冗余一份允许延迟的副本。

先别拆的情况：两块功能强一致、互相调用非常密。硬拆之后排错成本会高于收益。

拆出 item 与 cart

单体里商品和购物车是本地注入。拆开之后各自一个启动类、一份配置、一个库。

  1. 新建 item-service：迁入商品查询、上下架、库存扣减，暴露 HTTP 接口。
  2. 新建 cart-service：迁入购物车的增删改查。
  3. 加购时不再注入原来的商品 Service，改为 HTTP 查询价格和状态，通过后再写购物车表。
  4. 对外只传 DTO。item-service 的表实体留在自己工程里，不让购物车依赖对方的实现模块。
  5. 下单同样处理：order-service 调 item 扣库存、调 cart 删除已买商品，不要直接改对方的表。

模块上，公共工具放 hm-common，以后给别人调用的接口和 DTO 放 hm-api。这一步 RestTemplate 还写在调用方内部，接口稳定后再抽到 hm-api，改成 OpenFeign。

排错

现象 原因
连接被拒绝 端口错、服务没起、地址写成了容器内部才听得到的网卡
反序列化失败 字段名不一致，或 List 没使用 ParameterizedTypeReference
加购价格是空的 远程结果没判空，商品已下架仍写入了购物车
库存和购物车只有一边成功 已经是跨服务写，本地事务包不住对面的库

小结

单体适合把业务先做对。hmall 按登录、商品、购物车、订单、支付拆开，是为了独立发布和单独扩容。拆 item、cart 时连库一起分，调用改成 RestTemplate。地址写死只能用于把接口形状定下来，下一步用 Nacos 按服务名发现实例。
