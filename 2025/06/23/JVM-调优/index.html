JVM 调优

2025-06-23
  • JVM
本文总阅读量次

千淘万漉虽辛苦，吹尽狂沙始到金。

先有症状，再改参数

调优是用证据缩小范围：停顿变长、Full GC 变密、某一区 OOM，还是线程打满。没有基线数据时改 -Xmx，只是把问题推迟或搬到别的区域。

一次只改一个因素，在相同压力下对比 GC 日志和接口耗时。参数抄来一套叠加上去，无法知道是哪一项起了作用。

常用参数

参数 作用 注意
-Xms / -Xmx 堆初始大小 / 上限 线上常设成一样，避免运行中扩缩带来的抖动
-Xmn 年轻代大小 与 G1 的 Region 自适应不必强行一起用
-Xss 每个线程的栈大小 调大能缓解深层调用，但同样内存创建的线程更少
-XX:MetaspaceSize 元空间达到该值后触发回收的初始阈值 不是硬上限
-XX:MaxMetaspaceSize 元空间上限 类不断增多时用来让问题尽早暴露
-XX:MaxGCPauseMillis G1 的目标暂停 目标过小会导致收集过于频繁
-XX:+HeapDumpOnOutOfMemoryError OOM 时写出堆转储 配合 -XX:HeapDumpPath 指到磁盘充足的目录

JDK 8 默认收集器是 Parallel，JDK 9 及以后默认是 G1。要明确指定时使用 -XX:+UseG1GC 或 -XX:+UseParallelGC，不要两套同时抄进脚本。

堆只是进程内存的一部分。元空间、线程栈、直接内存、代码缓存都在 -Xmx 之外。容器内存上限要大于堆，并给这些区域留余量，否则进程会被系统杀掉，而 JVM 日志里看不到 Java heap space。

读日志时抓这几列，而不是从第一行逐字翻译：

  1. 收集类型：Young、Mixed 还是 Full。
  2. 收集前后各区占用，以及晋升到老年代的量。
  3. 单次暂停时间，Full GC 是否成串出现。
  4. 元空间是否只增不减。

年轻代每隔几秒收集一次、暂停十几毫秒，多数服务可以接受。老年代在每次年轻代收集后都明显上涨，且几乎不回落，再去区分是缓存设计如此，还是引用没放开。

四个命令各自负责什么

JDK 自带，先有进程号再查细节。

命令 用途
jps 列出 Java 进程与主类，确认打到的是目标进程
jstat 看各区使用率、Young / Full 次数与耗时，适合连续采样
jmap 堆直方图或导出堆转储；histo:live 会先触发一次 Full GC
jstack 线程栈，查死锁、阻塞在锁或 IO 上的线程

jmap -dump:live,format=b,file=logs/heap.hprof <pid> 会停顿业务，只在已经决定要分析泄漏时使用。直方图里按字节排序，看是不是某一两个类的实例数异常，再决定要不要转储。

jstack 多抓几次间隔数秒的快照。每次都停在同一处，才更像死锁或真阻塞；只出现一次可能是正常等待。

推荐步骤

  1. 定性。延迟升高、CPU 高、内存涨、还是直接 OOM。CPU 高要区分是业务计算还是 GC 线程。
  2. 留证。GC 日志、jstat 采样、必要时线程栈。OOM 打开堆转储。时间范围和发布、流量高峰对齐。
  3. 定位。堆涨看是泄漏还是缓存；暂停长看是 Young 太频繁还是 Full GC；线程多看池大小和 -Xss；元空间涨看类加载。
  4. 改一处。例如只把堆从 1G 调到 2G，或只切换到 G1。写下来改了什么。
  5. 复测。同一压测或同一时段流量对比暂停、Full GC 次数、接口耗时。没有改善就撤回，不把参数累加。

泄漏靠调大 -Xmx 只会晚一点爆。转储里某个集合被静态字段或线程池任务一直引用，应改引用关系或给缓存加淘汰，而不是继续加堆。

症状对照

现象 先看 方向
Young GC 很密、单次很短 分配速率、Eden 大小 先减临时对象
Young GC 单次很长 存活对象体积 年轻代是否过大、晋升是否失败
Full GC 成串出现 老年代能否回落、元空间 泄漏、无上限缓存，或堆过小
进程被系统杀掉，堆仍有空闲 容器上限、线程数、直接内存 给堆外留余量
CPU 高且大量时间在 GC jstat 里 GC 耗时占比 再决定收集器，并排除死循环

对照表用来缩小范围。同一行里的「方向」一次只试一个，无效就回到证据，不叠加下一行的参数。

不要这样调

  • 同时改堆大小、收集器、暂停目标、线程栈，出了问题无法归因。
  • 把开发机的参数原样搬到核心数、内存差一个数量级的机器上。
  • 为了消灭每一次 Young GC 把年轻代设得极大，单次暂停会变成明显卡顿。
  • 线上对健康进程频繁 jmap -dump:live，它本身就会打一次 Full GC。
  • 看到 System.gc 就全局禁用，却没确认直接内存框架是否还依赖它。

收集器能缓解停顿，不能代替正确的对象生命周期。日志证明暂停已经不是瓶颈时，应回到慢 SQL、锁和线程池，而不是继续加 JVM 参数。

小结

  • -Xms 与 -Xmx、栈、元空间上限，是最先认清的三个尺寸；堆之外的内存同样会撑满机器。
  • jps 找进程，jstat 看趋势，jmap 看对象，jstack 看线程。
  • 先定位再改一个参数，用同一负载验证；无效就撤回。
