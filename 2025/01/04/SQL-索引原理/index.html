SQL 索引原理

2025-01-04
  • SQL
本文总阅读量次

仰天大笑出门去，我辈岂是蓬蒿人。

B+ 树、聚簇和二级

InnoDB 用 B+ 树做索引。非叶节点只放键，用来指路，一页能装下很多键，所以树很矮。叶子之间用链表串起来，范围扫描沿叶子走。

聚簇索引的叶子就是整行数据，按主键有序。一张表只有一棵聚簇索引。二级索引的叶子是索引列加上主键。查询需要的列不在二级索引里时，用叶子上的主键再去聚簇索引取行，这一步叫回表。命中多少行，就大约再查多少次聚簇索引。

主键怎么选

没有显式主键时，InnoDB 选用第一个非空唯一索引；再没有，就生成 6 字节的隐藏行号。隐藏行号业务里用不了，二级索引仍然要带上它。表应自己声明主键。

主键会出现在每一棵二级索引里。它适合短、稳定、顺序增长。

  • 自增整数短，新行追加在叶子末尾，页分裂少。
  • 随机的长主键让插入落在叶子中间，页经常分裂，二级索引一并变大。
  • 修改主键等于在聚簇索引里删除再插入。用不会改的列做主键。

最左前缀

联合索引 (a, b, c) 先按 a、再按 b、再按 c 排序。查找从最左列连续用起，中间断开，右边的列就接不上。

条件 沿这棵索引能用到
a = 1 a
a = 1 AND b = 2 a、b
a = 1 AND b = 2 AND c = 3 a、b、c
b = 2 或只有 c 用不上，缺了 a
a = 1 AND c = 3 只用 a，b 空档后 c 接不上
a = 1 AND b > 2 AND c = 3 a 和 b；范围后面的 c 不能再定位

最后一行就是范围后的列：b 已经是范围，扫描起点不能再靠 c 缩小。扫描过程中仍可以用 c 做过滤。等值列放在范围列左边，索引才用得满。

覆盖索引和回表

查询列都在同一棵索引里时，不必回表，这就是覆盖索引。EXPLAIN 的 Extra 出现 Using index，表示这次没有回表。

上面的语句若有索引 (category_id, status, name)，name 已经在叶子上。二级索引筛出大量主键、又要回表取很宽的行时，随机读会盖过索引的好处，优化器可能改走聚簇索引。把经常一起查的列收进联合索引，是为了少回表；索引变宽后，每次写入都要多维护一棵树。

普通索引用不上的写法

写法 发生什么
对索引列套函数或表达式 无法按该列的索引顺序定位。MySQL 8.0 可以给表达式另建索引
字符串列与数字比较 列被转成数字，该列上的索引用不上
OR 有一侧没有可用索引 常常全表扫描；两侧都有索引时可能是 index_merge
LIKE '%杯' 前导模糊，B+ 树无法确定起点
LIKE '杯%' 可以走索引
联合索引里范围条件右边的列 不能继续用于定位

phone 是字符串时，和数字比较会转换这一列。数字列和字符串常量比较时，转换的是常量，索引仍可用。DATE(created_at) 改成 created_at 的范围条件，才能沿时间列定位。这些语句本身合法，优化器只是放弃对应的普通索引。

读 explain

type 是访问方式，key 是实际选中的索引，rows 是估计要检查的行数。rows 来自统计信息，是估计值，而且是检查行数，不是最终返回的行数。

type 含义
const 主键或唯一索引等值，至多一行
eq_ref 联表时按主键或唯一索引匹配，每个外层行对应一行
ref 普通索引等值，可能多行
range 索引上的范围扫描
index 扫描整棵索引树
ALL 全表扫描

key 为空，表示没有选中索引。rows 越小，估计的工作量越低；统计信息过旧时，数字会偏离实际。type 为 ALL 且 key 为空时，先看条件是否写在索引列上，以及是不是函数、隐式转换、前导模糊或 OR。Extra 里的 Using index 表示覆盖索引。

ref 说明走了普通索引的等值查找，key 给出索引名。再看 Extra 有没有 Using index，判断这次有没有回表。

小结

  • 聚簇索引存整行，二级索引存索引列和主键，缺列就要回表。
  • 主键宜短、稳定、顺序增长。联合索引从最左列连续使用，范围列右边不能再定位。
  • 覆盖索引看 Extra 的 Using index。函数、隐式转换、前导模糊和一侧无索引的 OR，会让普通索引用不上。
  • type 看访问方式，key 看用了哪棵索引，rows 看估计要检查多少行。
