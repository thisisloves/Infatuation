synchronized 与 ReentrantLock

两者都是可重入互斥锁：同一线程再次进入不会把自己锁死，获取几次就要释放几次。synchronized 进监视器、出监视器由编译器配对；ReentrantLock 必须在 finally 里 unlock，漏一次就把锁占死。

synchronized ReentrantLock
释放 出代码块自动放 必须手写 unlock
公平 非公平 构造参数可选公平锁
中断 等锁时不能被中断 lockInterruptibly 可响应中断
条件 一个等待集，wait / notify 多个 Condition，各自 await / signal
试锁 没有 tryLock、tryLock(timeout)

等 synchronized 的线程状态是 BLOCKED。等 ReentrantLock 停在 AQS 队列，状态是 WAITING 或 TIMED_WAITING。

公平锁按排队顺序发锁，吞吐更低，只有严格避免饥饿时才开。默认非公平：新来的线程可以插队，少一次挂起和唤醒。

Condition 把不同等待原因拆开。例如「队列空」和「队列满」各一个条件，signal 不会把等另一件事的线程叫醒。synchronized 只有一个等待集，做不到这种区分，只能 notifyAll 让所有人自己再判断。

能用 synchronized 说清的临界区就用它，JVM 对它有偏向锁、轻量级锁的优化。需要可中断、超时、多个条件队列时再换 ReentrantLock。读多写少可以再看 ReentrantReadWriteLock 或 StampedLock，那是后话。

volatile

volatile 管两件事：可见性、有序性。不管原子性。

写一个 volatile 变量会把本线程工作内存的修改刷到主内存；之后别的线程读它，能看到这次写之前的所有写入。这就是 happens-before：对 volatile 的写，先行发生于随后对它的读。

有序性靠内存屏障，禁止把后面的读写重排到这次写之前，也禁止把前面的读写重排到这次读之后。双重检查锁要的就是这条。

它不做复合操作。count++ 是读、加、写三步，两线程同时读到旧值，各写回一次，会丢更新。计数用 AtomicInteger 或加锁。

双重检查锁为什么必须 volatile。 没有它，另一个线程可能看到对象引用已经非 null，但构造方法里的字段写入被重排到赋值之后，于是拿到一个还没初始化完的实例。

外层 if 避免每次都加锁。内层 if 避免两个线程都通过外层后各 new 一次。volatile 保证 inst = new Lazy() 的构造完成先于引用被其它线程看见。静态内部类持有单例也可以懒加载，并且由类初始化锁保证安全，不一定非要手写 DCL。

JUC 里五个常用类型

记场景，不背类图。

  • CountDownLatch：一个或多个线程等 N 件事做完。countDown 到 0 后放行，计数不能重置，一次性。
  • CyclicBarrier：固定数量的线程互相等到齐再一起继续，到齐次数用完可以 reset 进入下一轮。和 Latch 的差别是「互相等」而不是「等别人」。
  • Semaphore：许可数。令牌还有剩余才能进入，用来限制同时访问某资源的线程数。
  • AtomicInteger：CAS 做自增、比较并设置。单个变量的原子更新，不需要互斥锁；ABA 或要同时改两个变量时再考虑别的办法。
  • ConcurrentHashMap：多线程同时读写的 Map。键和值都不能是 null；putIfAbsent、compute 把「先查再改」收成原子操作。

ThreadPoolExecutor 的七个参数

  1. corePoolSize：平时保留的线程数，即使空闲也不回收（除非允许核心线程超时）。
  2. maximumPoolSize：线程数上限，队列满了之后才继续新建，直到这个数。
  3. keepAliveTime：超过核心数量的空闲线程，活过这段时间就被回收。
  4. unit：上面这段时间的单位。
  5. workQueue：核心线程都在忙时，新任务进的队列。
  6. threadFactory：给线程起名、设是否守护、设未捕获异常处理器。不要用匿名默认工厂，出了问题线程转储里全是 pool-1-thread-x。
  7. handler：队列也满、线程数也到上限时，对新任务执行的拒绝策略。

任务进来的顺序容易讲反，按这个记：

无界队列几乎永远放得下，于是 maximumPoolSize 和 keepAliveTime 形同虚设，线程数停在核心大小，压力全部堆在内存里的队列上。

四种拒绝策略

AbortPolicy 是默认：抛 RejectedExecutionException，调用方立刻知道被拒。CallerRunsPolicy 让提交任务的那条线程自己跑，提交速度会被拖慢，形成反压。DiscardPolicy 直接丢掉。DiscardOldestPolicy 丢掉队列里最旧的一个再尝试放入，排队顺序有业务含义时不能用。

生产上更常见的是自己实现 RejectedExecutionHandler：打日志、写入有界的备用存储、或把异常带回调用方。静默丢任务是事故。

不要用 Executors 的无界工厂

Executors.newFixedThreadPool 和 newSingleThreadExecutor 用的是无界 LinkedBlockingQueue。任务提交得比处理快时，队列无限变长，最终 OutOfMemoryError，而且最大线程数起不到保护作用。

newCachedThreadPool 相反：队列是 SynchronousQueue，不存任务，最大线程数是 Integer.MAX_VALUE。突发流量会为每个任务新建线程，同样把内存打满。

newScheduledThreadPool 用的也是无界队列。最大线程数虽标成 Integer.MAX_VALUE，队列不满根本不会去创建那么多线程，任务堆积时先把内存打满。

允许上生产的写法是直接 new ThreadPoolExecutor：核心数按 CPU 或 IO 比例估计，队列用有界的 ArrayBlockingQueue，拒绝策略明确，线程工厂写出业务名字。提交之后要 shutdown，否则非守护线程会把进程留住；已提交的任务用 awaitTermination 等完，不要 shutdownNow 完就当全部执行过。
