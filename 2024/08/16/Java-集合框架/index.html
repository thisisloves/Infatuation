Java 集合框架

2024-08-16
  • Java
本文总阅读量次

空山新雨后，天气晚来秋。

Collection 与 Map

Map 不是 Collection 的子接口。集合框架在最上层分成两支：一组元素，和一组键值。

Set 的判等靠 equals 和 hashCode（TreeSet 则靠比较器）。Map 的键同样如此。keySet()、values()、entrySet() 是原 Map 的视图，改视图会影响原 Map，不是拷贝。

怎么选 List、Set、Map

先看数据关系，再看要不要排序、要不要下标。

  • 要按下标访问、允许重复：List。
  • 只要唯一性：Set。要排序用 TreeSet，要保持插入顺序用 LinkedHashSet。
  • 要按键查值：Map。排序用 TreeMap，保持插入或访问顺序用 LinkedHashMap。
  • 两端进出用 ArrayDeque，不要用 Stack，也不要用 LinkedList 当栈。
  • 带优先级用 PriorityQueue，堆顶才是优先级最高的元素，遍历顺序不是排序结果。

List 的「有序」指插入顺序稳定、有下标。TreeSet / TreeMap 的「有序」指按键的比较结果排列。两词不要混用。

ArrayList 与 LinkedList

ArrayList 是动态数组。无参构造时内部先是空数组，第一次添加才分配到默认容量 10，之后不够按约 1.5 倍扩容并拷贝。随机读 get(i) 是 O(1)；尾部追加均摊 O(1)；中间插入要搬移后续元素，O(n)。

LinkedList 是双向链表，节点另存 prev、next。真正拿到节点后，断开或接上是 O(1)；但 List 的 get(i)、按下标插入都要先从头或从尾走到那个位置，仍是 O(n)。每个元素多一个节点对象，缓存也不如连续数组。

所以绝大多数列表用 ArrayList。只在已经持有结点、或频繁在两端插入删除时，链表才有优势；两端操作更常见的选择是 ArrayDeque。

HashSet 与 TreeSet

HashSet 内部是 HashMap，元素当键，值是一个固定的哑对象。无序，允许一个 null，增删查均摊 O(1)。判重用 hashCode 再 equals。

LinkedHashSet 在桶之上用双向链表串起插入顺序，迭代顺序稳定，开销比 HashSet 略大。

TreeSet 内部是 TreeMap，红黑树，按自然顺序或构造时传入的 Comparator 排序，增删查 O(log n)。自然顺序下不允许 null，因为 null 无法和别的元素比较。比较器与 equals 应一致，否则「比较为 0」和「equals 为 false」会让 Set 的语义分裂。

HashMap、TreeMap、LinkedHashMap

三者都实现 Map，差别在键怎么放。

实现 结构 顺序 键的 null 复杂度
HashMap 数组 + 链表 / 红黑树 无序 允许一个 均摊 O(1)
LinkedHashMap 同上，再加双向链表 插入序，或访问序 允许一个 均摊 O(1)
TreeMap 红黑树 键的排序 自然顺序不允许 O(log n)

LinkedHashMap 构造参数 accessOrder 为 true 时，get 会把节点挪到链表尾，适合按访问时间淘汰的缓存。TreeMap 能做范围查询：subMap、ceilingKey、firstKey。键的类型没有稳定哈希、又要排序时用它；只为查找用 HashMap。

哈希桶、树化阈值、扩容的细节放在 HashMap 那一篇，这里只记选型。

fail-fast

ArrayList、HashMap 的迭代器在创建时记下 modCount。遍历过程中如果有人增删元素，结构修改会让 modCount 加一，下次 next 发现和预期不一致，就抛 ConcurrentModificationException。

这是尽力检测，不是加锁，也不能当成同步手段。单线程里用迭代器自己的 remove 是安全的，它会同时修正预期的修改次数。按下标的 for 不检查 modCount，但边遍历边 remove(i) 会跳过元素，同样是错的。

另一个线程改集合时，这次检测仍可能漏报：它只在迭代器前进时才看计数。所以异常用来暴露 bug，不能用来保证线程安全。

要线程安全时怎么选

手段 做法 适合
Collections.synchronizedXxx 用同一把锁包住每个方法 遗留代码快速包一层；迭代仍要自己在外面加锁
Vector / Hashtable 方法上全是 synchronized 老 API。并发度差，新代码不用
ConcurrentHashMap 桶级锁或 CAS，读多写多都能扛 并发 Map 的默认选择
CopyOnWriteArrayList 写时复制整段数组，读不加锁 读远多于写，迭代期间允许看到旧快照

Collections.synchronizedList 的迭代器仍是 fail-fast。遍历必须手动包住整段迭代，只锁住单个 get 不够。

CopyOnWriteArrayList 的迭代器拿的是创建时的数组快照，不会抛 ConcurrentModificationException，也看不到迭代开始之后的写入。写一次就复制整个数组，列表一大、写一频繁就会又慢又费内存。监听器列表这种「几乎只读、偶尔注册」才合适。

队列侧的并发需求用 BlockingQueue：有界用 ArrayBlockingQueue，无界要自己清楚容量风险。不要用同步包装类去包一个会在多线程里频繁改结构的 ArrayList 来冒充并发容器。
