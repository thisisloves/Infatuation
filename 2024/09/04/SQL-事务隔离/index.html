SQL 事务隔离

2024-09-04
  • SQL
本文总阅读量次

秋水将晚，云断南归雁，一纸青山，却有红尘万千。

隔离级别在防什么

  • 事务是一组一起提交或一起回滚的语句。并发时，一个事务能看见另一个事务的哪些改动，由隔离级别规定。
  • 标准 SQL 定义了四种级别。MySQL InnoDB 的默认是 REPEATABLE READ。PostgreSQL、Oracle 的常见默认是 READ COMMITTED。
  • 下面「是」表示这个级别下仍可能出现该现象。
隔离级别 脏读 不可重复读 幻读
READ UNCOMMITTED 是 是 是
READ COMMITTED 否 是 是
REPEATABLE READ 否 否 是
SERIALIZABLE 否 否 否
  • 级别从低到高，限制逐级变严，并发能重叠的程度逐级变小。SERIALIZABLE 把读写串成可串行的结果，冲突时往往等待或失败。

脏读

  • 事务 A 改了数据还没提交，事务 B 已经把这个未提交的值读走。A 若回滚，B 手里的值在库里从未存在过。
  • 例：发薪事务把账户改成 5000 后尚未提交，另一事务读到 5000。发薪发现金额有误并回滚，再以 2000 提交。读到过 5000 的那次就是脏读。
  • READ COMMITTED 及以上只读已经提交的版本，这条路径被挡住。

不可重复读

  • 事务 B 两次读取同一行，中间事务 A 修改该行并提交，B 的两次结果不同。
  • 例：扣款前读到余额 2000。另一事务把这 2000 转走并提交。扣款语句再读同一行，余额已是 0。
  • 这是对已有行的 UPDATE。REPEATABLE READ 在同一事务里保持第一次读到的快照，普通的再次 SELECT 仍看到 2000。真正扣款若使用当前最新版本加锁，仍可能发现钱已经不在，业务上要用「更新时检查余额」而不是只相信事务开头的那次读取。

幻读

  • 事务两次用同一条件圈定行集合，中间有别的事务插入或删除并提交，第二次多出或少了行。标准里的 REPEATABLE READ 不保证挡住这种现象。
  • 例：按「本月」汇总消费得到 80，同一事务稍后按同一条件列出明细。其间插入并提交了一笔 1000，明细的行集合和第一次汇总对不上。
  • 它和不可重复读的差别在于：后者是某一行的列值变了，前者是满足条件的行数变了。
  • InnoDB 的 REPEATABLE READ 对普通一致性读使用事务开始后第一次读的快照，再次 SELECT 通常看不到新插入的行。对 SELECT ... FOR UPDATE 这类加锁读，用临键锁挡住间隙里的插入。因此在 InnoDB 上，很多教材里的幻读演示不会按标准字面出现，换到 READ COMMITTED 或别的引擎又会看到。不要把「InnoDB 的 RR」写成「所有数据库的 RR 都没有幻读」。

怎么设置

  • MySQL 也可用 SET SESSION TRANSACTION ISOLATION LEVEL ... 改变本会话默认值。全局默认改动要和连接池里已经建好的会话区分开。
  • 单条语句的读一致性，解决不了「先读余额、再按旧余额更新」的丢失更新。这种要在更新条件里带上版本号或旧值，或对那一行 FOR UPDATE。

常见坑

  • 隔离级别不代替约束。两个事务同时插入同一主键，靠唯一索引拒绝第二份，和幻读是否可见是两件事。
  • MyISAM 没有事务隔离这一说，级别设了也不会按 InnoDB 的方式回滚。
  • 长事务一直开着 REPEATABLE READ，undo 里的旧版本不能被清掉，并发写入会把历史版本越堆越长。读完就提交。

两个会话对照一次

  • 读已提交下，A 的第二次查询看到 0。把 A 的级别改成可重复读，InnoDB 的第二次普通查询仍看到事务开始时的余额。
  • 查看当前级别：SELECT @@transaction_isolation;。SET TRANSACTION 只影响下一次事务，SET SESSION 影响本连接之后的事务。连接池会复用连接，会话级修改可能落到下一个请求上。

快照读和加锁读

  • 普通 SELECT 在 InnoDB 里读快照，不加行锁。SELECT ... FOR UPDATE 读当前最新行并加排他锁，用来做「读到之后马上改」。
  • 可重复读挡住的是快照上的不可重复读和多数幻读。扣款、库存这种必须看最新值的语句，仍然要把条件写进 UPDATE（WHERE id = 1 AND balance >= 2000），用受影响行数判断有没有成功。
  • 受影响行数为 1 才算扣成。为 0 表示余额已不够或行不存在，应用提示失败并结束事务。这条更新在各个隔离级别下都看当前已提交的最新值，不依赖事务开头那次 SELECT。
  • 只把隔离级别调高，解决不了丢失更新：两个事务都按自己读到的旧余额写回，后提交的会盖住先提交的。把增减写进一条 UPDATE，或对那一行 FOR UPDATE。
