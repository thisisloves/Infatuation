LIMIT 的两个参数

  • MySQL 里 LIMIT 放在查询最后，在 ORDER BY 之后生效。
  • 旧写法 LIMIT 偏移, 行数 和 LIMIT 行数 OFFSET 偏移 等价。两个参数的顺序相反，LIMIT 1, 2 是偏移 1、取 2 行，不是「第 1 页取 2 行」。
  • 不写 ORDER BY 时，每一页的成员没有保证。插入、删除或执行计划变化后，同一页会重复或遗漏。

按页码计算偏移

  • 第 n 页、每页 m 行时，偏移是 (n - 1) * m。MySQL 的 LIMIT 要求这里是非负整数常量（预处理语句里可以是占位符，存储过程里可以是整型变量），不能把 (n - 1) * m 直接写进语句当表达式。在应用里算好再传入：
  • 页码从 1 开始。偏移为负时语句报错。请求远超总行数的页码时，结果是空集，这是正常情况。

深偏移为什么慢

  • LIMIT 100000, 100 仍然要找出排序后的前 100100 行，再丢掉前 10 万行。偏移越大，读到又扔掉的行越多。高并发下反复扫这 10 万行，延迟会随页码上升。
  • 只给「上一页 / 下一页」、且排序键稳定时，用键集分页：记住上一页最后一行的键，下一页从它后面接着取。
  • 这里的 LIMIT 2 就是这一页的大小，不要再加偏移。WHERE id > 4 ORDER BY id LIMIT 2, 2 会在「id 已大于 4」的集合里再跳过 2 行，页与页之间对不齐。
  • 键集分页要求排序列唯一。单靠 age 时，年龄相同的行没有稳定的「下一条」。写成 WHERE (age, id) > (22, 4) ORDER BY age, id，把主键接在排序键后面。id 有空洞（删过行）不影响正确性，因为它比的是键，不是行号。

常见坑

  • ORDER BY id LIMIT 2 OFFSET 1 的「第 2、第 3 行」指排序后的位置。id 若是 10、20、30，这两行的 id 是 20 和 30，不是 2 和 3。
  • 偏移分页在两页请求之间有人插入了更小的 id，第二页会重复上一页的最后一行。键集分页按键续接，不会整页后移。
  • 总页数需要 COUNT(*)，大表上另算一次。列表查询本身不要为了页码把全部主键查回应用内存。
  • 覆盖索引能减少回表：SELECT id, name ... ORDER BY id 若有 (id, name) 索引，深分页的代价会小一截，但大偏移仍要数过那些被跳过的索引项。

应用里算出偏移再传入

  • LIMIT ? 是行数，OFFSET ? 是偏移。两个问号的旧形式 LIMIT ?, ? 则是先偏移、后行数，和带名字的写法顺序相反。
  • 用户变量不能直接写进 LIMIT @skip, @take。要么在应用里拼好整数，要么走预处理语句或存储过程参数。页码、页大小先校验成非负整数，再绑定，避免把其它 SQL 拼进语句。
  • 页码从 1 开始。调用方传入 0 或负数时在应用里拒绝，不要让数据库收到负的偏移。
