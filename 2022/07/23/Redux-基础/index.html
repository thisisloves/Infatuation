Redux 基础

2022-07-23
  • Redux
本文总阅读量次

斜阳独倚西楼，遥山恰对帘钩。人面不知何处，绿波依旧东流。

Redux 管的是什么

Redux 把应用里需要共享、需要回溯的状态放进一个 store。界面不直接改这份状态。界面派发一个描述「发生了什么」的 action，reducer 纯函数算出下一份状态，订阅者再渲染。

它不是 React 的一部分。组件本地的输入草稿、开关，用 useState 更合适。服务端才是权威的数据，也不必整份抄进 Redux。多个相距很远的组件要读同一份客户端状态、或更新规则已经复杂到需要集中测试时，再引入 store。

三条约束

  1. 单一 store。 state 是普通对象（或由 reducer 返回的任意可序列化值）。不要把 Promise、函数、类实例塞进 state，时间旅行和持久化都会断。
  2. state 只读。 改变它的唯一办法是 dispatch(action)。action 是带 type 字段的普通对象，约定上用 payload 带数据。
  3. 用纯函数计算下一份状态。 reducer (state, action) => nextState 不发请求、不改入参、不读 Date.now() 这类每次不同的值。异步放在 thunk、saga 或组件里，完成后再 dispatch 一个结果 action。

数据怎么流

用户点击 → dispatch({ type: 'counter/add', payload: 1 }) → store 调用 reducer → 得到新 state → useSelector 发现选中的值变了 → 组件渲染。没有「reducer 调用组件」这条反向通道。组件想读状态，就订阅；想改状态，就派发。

现在的官方写法是 Redux Toolkit

手写 createStore + switch + 不可变更新仍然能跑，但 Redux 核心包已把 createStore 标为不推荐。新代码用 Redux Toolkit：configureStore 配好 thunk 和开发工具，createSlice 用 Immer 让你在 reducer 里写「修改草稿」的语句，库会产出新的不可变 state。

Immer 的草稿只能在 createSlice / createReducer 里那样写。手写 reducer 若直接 state.value++ 再返回 state，引用不变，界面不更新，外部持有的旧 state 也被污染。

请求谁先返回，仍是竞态。reducer 只按收到的 action 顺序算出下一份 state，不会丢掉过期响应。要忽略旧请求，在发请求的地方用序号或 AbortController，不要指望 store 帮你排序。

和组件状态的边界

一个页面用的筛选条件，放在该页面的 state 或 URL。登录用户、全局通知、多页共享的缓存，再进 store。把所有 useState 都搬进 Redux，只会让每次按键都经过全局订阅。
