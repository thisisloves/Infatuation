React 渲染机制

2022-03-13
  • React
本文总阅读量次

不念则忘 不念勿想。

一次 setState 之后发生什么

调用 setState 或 dispatch 只是往当前 Fiber 的更新队列里推一条 update，并通知根调度。组件函数不会在这一行立刻再执行。当前函数里读到的 state 仍是这次渲染的快照。

接着 Scheduler 决定这批更新走同步循环还是并发循环。选中的车道记为 renderLanes，从根 Fiber 开始 render。

render 阶段

对每个 Fiber 调用 beginWork：

  1. 类组件走 processUpdateQueue 算出 memoizedState，再调 render()。
  2. 函数组件按顺序执行 Hooks，再执行函数体，得到子元素。
  3. 子元素和上一轮 children 做同层 Diff，生成或复用子 Fiber，标上 Placement / Update / Deletion。
  4. completeWork 为宿主节点准备 DOM（首次创建 DOM，更新则对比属性，先记下来，commit 再写）。

render 阶段不让用户看见中间态。并发渲染中，这个阶段可以暂停，也可以因为更高优先级而从 current 树重做。因此函数体里不能有订阅、请求、随机决定布局这类副作用。

子树的 props 没变、没有待处理车道时，可以 bailout：跳过该 Fiber 的渲染，把子车道冒泡上去。React.memo、PureComponent、shouldComponentUpdate 影响的是这一步要不要跳过，它们不改变 commit 的规则。

commit 阶段

render 得到一棵完整的 WIP 之后进入 commit，三段都不让出：

  1. before mutation：getSnapshotBeforeUpdate，读旧 DOM。
  2. mutation：按 flags 插入、更新、删除 DOM，处理 ref 的拆卸。
  3. layout：此时 DOM 已是新的，浏览器尚未绘制。跑 useLayoutEffect、componentDidMount、componentDidUpdate，设置 ref。这里改 DOM 用户看不见闪烁，但会推迟绘制，不宜做重计算。

然后浏览器绘制。绘制之后 React 再跑 passive 阶段：useEffect 的清理函数和效果函数。清理函数先于下一次效果，也在卸载时执行。

什么会触发渲染

  • 根上的 root.render。
  • 类组件 setState、forceUpdate。
  • 函数组件的 useState / useReducer dispatch。
  • useSyncExternalStore 的 store 通知。
  • 祖先提供的 context 值变化（按引用比较）。

父组件渲染，子组件默认会跟着执行函数体。这不等于 DOM 一定改写：props 相同的宿主节点可以只复用 DOM。要跳过子函数执行，需要 memo / shouldComponentUpdate，并且传下去的 props 引用稳定。

批处理发生在调度之前

同一个事件、同一个 setTimeout、同一个 Promise 回调里的多次 dispatch，React 18 在 createRoot 下合成一次 render。这是渲染次数的合并，不是「state 变成异步 API」。flushSync 会在回调返回前完成一次同步 render + commit，从而把前后更新拆开。

和绘制的时序

时机 能做的事
render 纯计算，可能重复
layout 阶段 读布局、同步改 DOM
浏览器绘制 用户看见新画面
useEffect 订阅、请求、写日志

在 useEffect 里改 state 会再触发一次渲染，用户可能先看到中间画面。能在绘制前算出来的，放在渲染期间或 useMemo；必须碰 DOM 又不能闪一下的，放在 useLayoutEffect。
